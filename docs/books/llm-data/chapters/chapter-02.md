# 第 2 章 分词、多模态编码序列与样本打包账本

<p class="chapter-summary">深入大模型输入层的微观 Token 经济学：对比词表规模与语种/代码/数学的分词生育率（Fertility）与字节压缩比，量化图像动态切片、视频抽帧与音频 Codec 的跨模态序列开销，掌握 Document Packing 块内注意力掩码与 FIM 重排机制，并逐一排雷对话、工具、思考与多模态占位模板的静默毒化缺陷。</p>

很多数据团队以为只要把清洗好的 JSONL 交给训练框架，数据工程的任务就结束了。现实中却屡屡发生令人扼腕的事故：中文业务模型因词表压缩率太差，同等上下文窗口的有效容量只有竞品的一半、推理账单翻倍；多模态训练未算清高分截图的视觉 Token 膨胀，导致序列截断吃掉了用户问题本身；甚至因为聊天模板里多了一个不可见的空格或漏掉一条块对角掩码，让千卡集群跑完三周、训练 Loss 平滑下降，上线后模型却满口胡言或永远停不下来。本章把“模型入口前的最后一公里”彻底量化为清晰账本与工程红线。

## 2.1 分词器词表规模、语料配比与生育率（Fertility）账本

现代主流大模型普遍采用 **Byte-level BPE（字节级字节对编码）** 或基于字节回退的 Unigram 分词器，确保任意 UTF-8 字节流零 `<unk>` 丢失。然而，决定分词器工程表现的绝不仅是算法本身，而是**词表大小 $|V|$、训练语料配比以及正则预分词（Pre-tokenization）规则**。

衡量分词编码效率的两个核心指标是字节压缩比（Bytes-Per-Token, $\mathrm{BPT}$）与<a class="term-ref" href="/books/llm-data/glossary#fertility" title="分词器将单个自然语言词或语义单元平均切分出的 Token 数量；越低代表压缩率越高、有效上下文越长">分词生育率（Fertility, $f_{\text{fert}}$）</a>：

$$
\mathrm{BPT} = \frac{\text{UTF-8 原始字节数}}{\text{分词后 Token 数}}, \qquad
f_{\text{fert}} = \frac{\text{分词后 Token 数}}{\text{语义词 / 汉字数}}
$$

生育率越低（或 $\mathrm{BPT}$ 越高），意味着同一段语义占用的 Token 越少——这同时带来三重红利：**同等预训练步数吞下更多真实知识、同等上下文窗口塞进更长文档、在线自回归推理的解码步数与首字/总延迟线性下降**。但词表绝非越大越好：在隐藏维度 $d_{\text{model}}$ 下，输入嵌入与输出头（Unembedding LM Head）的参数量与显存直接按 $2 \cdot |V| \cdot d_{\text{model}}$ 膨胀（在 $d=4096$、BF16 下，$|V|=256\text{K}$ 仅词表两头就占去 **2.1B 参数与 4.2 GB 静态权重**，对 3B/7B 端侧小模型造成沉重开销），且尾部低频词难以获得充分梯度更新，易演化为推理时胡言乱语的“幽灵 Token（Glitch Tokens）”。

| 典型分词器演进代际 | 词表 $|V|$ | 英文 $f_{\text{fert}}$ / BPT | 中文（每字 Token / BPT） | Python 代码 BPT | 数学数字切分策略 |
| --- | --- | --- | --- | --- | --- |
| **早代英文主导**（Llama-2 级） | 32K | ~1.30 / ~4.0 | ~1.45 / **~2.0**（单字常拆 2–3 字节） | ~3.0（缩进吃大量 Token） | 任意多位合并（破坏位值算术对齐） |
| **均衡双语/多语**（Llama-3 / GPT-4o 级） | 128K–200K | ~1.18 / ~4.5 | ~0.72 / **~4.1**（高频双字词整切） | ~4.2（多空格缩进合并） | 1–3 位分段或单数字独立切分 |
| **中英代码深度优化**（Qwen2.5/3 / DeepSeek-V3） | 128K–152K | ~1.20 / ~4.4 | **~0.58 / ~5.1**（极高中文压缩） | **~4.5**（关键字+缩进联合） | 严格单数字（0–9）切分，对齐进位逻辑 |

### 数值算例：中文分词生育率如何直接改变推理与上下文账单

假设一份 10 万汉字（UTF-8 约 300 KB）的中文法律合同输入模型并生成 2,000 字审查报告：
- **使用早代 32K 英文词表**（每汉字 $f_{\text{fert}} \approx 1.45$）：输入瞬间膨胀至 **$145{,}000$ tokens**，直接撑爆 128K 上下文窗口；生成 2,000 字需自回归解码 **2,900 步**。
- **使用中英优化 152K 词表**（每汉字 $f_{\text{fert}} \approx 0.58$）：输入仅占 **$58{,}000$ tokens**（不足 128K 窗口的一半，KV Cache 显存直降 **60%**）；生成 2,000 字仅需 **1,160 步**，在线推理总延迟与单次 API 成本同步压低 **$2.5\times$**（联动 [《LLM 推理工程》](/books/llm-inference/) 的解码带宽瓶颈分析）。

**分词器训练的三条核心数据工程铁律**：
1. **单数字独立预分词**：若允许 BPE 把 `2026` 合并成一个 Token 而把 `2027` 拆成 `20` + `27`，模型做多位数算术时必须死记数千种不规则映射；现代推理模型均在正则预分词中强制**单数字 0–9 独立成 Token**（或严格右对齐 3 位切分），为算术泛化扫清障碍。
2. **代码连续空白符特化**：Python、YAML 与缩进表格存在海量 4/8 空格缩进；在预分词正则中允许合并连续空格，可立省约 15%–25% 的代码上下文预算。
3. **跨语种温度平滑采样**：训练分词器的语料绝不能按原始互联网比例喂入——英文占比过高会把中日韩与小语种常用词挤出词表。工程上对语种分布施加温度平滑 $p_l^\tau$（$\tau \approx 0.3\text{–}0.5$）并显式提高代码与 LaTeX 符号占比，确保目标业务语言拥有低生育率。

### 预训练词表预留槽位（Reserved Special Tokens）工程约定

在冻结预训练分词器时，务必提前在词表末尾预留 **128–256 个不可拆分的保留特殊位**（如 `<|reserved_special_token_0|>` 至 `<|reserved_special_token_255|>`），并将总词表大小 $|V|$ 向上对齐到 **64 或 128 的整数倍**（如 `151,936` 或 `128,256`）以最大化 GPU Tensor Core 矩阵乘效率。这样在进入后续多模态扩展、长思维链（`<think>` / `</think>`）或 Agent 工具协议升级时，只需给预留槽位赋予新语义别名即可零重构接入，彻底规避“后期扩词表重初始化 Embedding / LM Head 导致底座分布震荡”的工程噩梦。

## 2.2 多模态编码序列 Token 账本（图 / 视频 / 音频）

当模型升级为原生多模态（VLM / Omni）底座后，所有视觉与声学信号在进入 Transformer 主干前，都必须映射为与文本共享同一条序列长度预算的离散或连续 Token。若不提前算清这笔账，长图文与长视频批次会瞬间引爆显存 OOM，甚至在截断时把排在图像后面的用户提问直接切掉。

按 [核心公式与数据账本速查卡](/books/llm-data/toolkit/formulas-and-ledgers) 统一口径（以 ViT Patch $p\times p$ 与 $s_{\text{pool}}\times s_{\text{pool}}$ 空间合并为例）：

$$
T_{\text{img}}(H, W) = \left\lceil\frac{H}{p}\right\rceil \left\lceil\frac{W}{p}\right\rceil \cdot \frac{1}{s_{\text{pool}}^2} + T_{\text{meta}}, \qquad
T_{\text{vid}}(L_{\text{sec}}, f_{\text{fps}}) = L_{\text{sec}} \cdot f_{\text{fps}} \cdot T_{\text{frame}}, \qquad
T_{\text{aud}}(L_{\text{sec}}) = L_{\text{sec}} \cdot f_{\text{codec}}
$$

其中 $T_{\text{meta}}$ 为图像起止符、行换行符（newline token）及全局缩略图占位符开销。不同模态与分辨率策略下的典型 Token 账本如下：

| 模态与场景 | 典型编码配置 | 单样本 Token 消耗 | 等价纯中文文本量 | 数据打包与工程注意要点 |
| --- | --- | --- | --- | --- |
| **常规自然图** | $448\times 448$，$p=14$，$2\times 2$ 池化 | **$T_{\text{img}} = 256$**（+meta） | ~440 汉字 | 适合通用图文对，但会彻底糊掉密集小字与 UI 按钮 |
| **高分文档/GUI（<a class="term-ref" href="/books/llm-data/glossary#dynamic_resolution" title="不把高分图像粗暴压缩为固定小正方形，而是按长宽比自适应切分为若干标准图块加全局缩略图">AnyRes 动态切片</a>）** | 4 张 $448^2$ 切片 + 1 张全局图（或原生 $1120^2$） | **$1{,}280\text{–}1{,}600$** | ~2,200–2,800 汉字 | 必须逐图精准匹配 `<\|image_pad\|>` 个数，且按分辨率分桶防负载倾斜 |
| **1 分钟常规视频** | $L_{\text{sec}}=60$，$1\text{ fps}$，单帧压至 $128$ tok | **$T_{\text{vid}} = 7{,}680$** | ~1.3 万汉字 | 若提到 2 fps + 256 tok/帧，10 分钟视频即达 **307,200 tokens**！需动态抽帧（第 13 章） |
| **1 分钟语音（单码本）** | $25\text{ Hz}$ 声学 Codec（如 Mimi / Qwen-Audio） | **$T_{\text{aud}} = 1{,}500$** | ~2,600 汉字 | 若采用 $K=8$ 码本串行展平将膨胀至 12,000 tok；<a class="term-ref" href="/books/llm-data/glossary#full_duplex_audio" title="记录双方同时听与说、包含自然打断、插话与毫秒级时序对齐的双声道语音语料">全双工语音</a>需双流并行帧对齐 |

### 数值算例：多模态混合 Batch 的跨 Rank 计算失衡账

在训练<a class="term-ref" href="/books/llm-data/glossary#interleaved_data" title="保留原始网页或论文中文本段落与多张配图自然先后顺序的连续多模态序列">图文交错文档</a>或视频理解批次时，假设数据并行有 8 张 GPU，每卡序列上限 $L = 16{,}384$：如果 Rank 0 恰好抽到 10 页高分 PDF 截图（共消耗 $10 \times 1{,}600 = 16{,}000$ 视觉 Token，需驱动 400M ViT 执行 64,000 个 Patch 前向），而 Rank 1 抽到纯文本长文（ViT 计算量为 0），那么在反向传播 All-Reduce 屏障处，Rank 1 会长时间空转等待 Rank 0，整机 MFU 暴跌 20%–35%！工业级多模态打包器必须在 DataLoader 阶段执行**双约束负载均衡（Dual-budget Packing）**——让每个 Rank 同时对齐“总序列 Token 数 $\approx L$”与“视觉 Patch 总数 $\approx P_{\text{target}}$”，并在纯文本步插入极小哑元图像或分离梯度同步，彻底抹平跨卡木桶效应。

## 2.3 样本打包、块内注意力掩码与 FIM 重排

自然网页与代码文件的长度呈剧烈长尾分布（中位数仅 400–800 tokens，而上下文窗口动辄 8K–128K）。如果每条样本单独补齐 `<pad>` 至最大长度，高达 **35%–70%** 的矩阵乘法算力会被白白浪费在毫无意义的填充位上。因此，预训练与大规模 SFT 几乎全面采用 **Document Packing（样本打包）**：将多篇短文档首尾相接、以 `<eos>` 分隔，通过 Best-Fit 装箱算法拼满目标长度 $L$（如 8,192）后再送入 GPU，将 Padding 浪费压到 1% 以下。

然而，**裸奔打包（Naive Packing）暗藏严重的注意力污染与位置偏移缺陷**：
1. **跨文档串扰（Cross-Document Leakage）**：在朴素下三角因果掩码下，排在后面的 Doc B（一段 Python 代码）可以完整地 Attend 到前面毫不相干的 Doc A（一篇美食菜谱），迫使注意力头去分配概率质量给伪跨文档关联，显著拉坏长上下文检索与少样本上下文学习能力。
2. **RoPE 位置 ID 漂移**：如果不重置位置编号，Doc B 的首个 Token 会带着 `pos = 3,521` 的巨大绝对旋转位置进入网络，破坏模型对“文档开头”的归纳偏置。

治本方案是标配<a class="term-ref" href="/books/llm-data/glossary#intra_doc_masking" title="在将多篇不相关文档打包进同一条固定长度训练序列时，于注意力矩阵中阻断跨文档 Token 互见的块对角掩码">块内注意力掩码（Intra-document Attention Masking）</a>与**位置 ID 边界归零（Position ID Reset）**。借助 FlashAttention-2/3 的变长接口 `flash_attn_varlen_func`，无需在显存中物化 $O(L^2)$ 巨型二维掩码矩阵，只需向内核传入一维累计长度数组 `cu_seqlens = [0, n_A, n_A + n_B, L]`，即可在**零额外显存、甚至比稠密下三角更快**（直接跳过了被屏蔽的跨文档块矩阵乘！）的前提下，实现严格的块对角注意力隔离。

### 代码预训练的 <a class="term-ref" href="/books/llm-data/glossary#fim" title="将代码拆分为前缀、中段与后缀并重排为 PRE-SUF-MID 格式，使因果模型原生具备双向上下文代码补全能力">FIM（Fill-in-the-Middle）</a> 重排

对于代码预训练语料，单纯从左到右自回归只能学“接着往后写”，却无法胜任 IDE 光标插在函数中间的“看前又看后”代码补全。FIM 通过对 **50%–70%** 的代码文档随机选择两个切分点，将原文档拆为 `(Prefix, Middle, Suffix)` 并以 **PSM**（`<PRE> Prefix <SUF> Suffix <MID> Middle <EOT>`）或 **SPM**（`<PRE> <SUF> Suffix <MID> Prefix Middle <EOT>`）格式重排，使因果 LM 在完全不改网络结构、也不损害从左到右生成能力的前提下原生习得中段填空。切记三条硬约束：① 在字符或 Token 边界切分，绝不能把多字节 UTF-8 汉字拦腰劈断；② FIM 控制符必须注册为不可拆分的 Special Token；③ 对长代码仓（第 4 章）优先在函数体或语句块边界采样切点，贴合真实补全分布。

## 2.4 对话、工具、思考与多模态模板的“静默毒化”排雷

如果说洗数漏洞会让模型“学得慢”，那么**模板与掩码错误（Silent Poisoning Bugs）**则会让模型在 Loss 曲线看起来一切正常的情况下彻底瘫痪。工程复盘中，超过半数的后训练与多模态“玄学回退”都源于以下五类隐蔽缺陷：

| 静默毒化类型 | 常见代码误写 | 训练期伪装现象 | 推理期灾难表现 | 自动化拦截断言 |
| --- | --- | --- | --- | --- |
| **1. 双重 BOS / 丢失停止符** | 手动拼接 `<bos>` 后又设 `add_special_tokens=True`；或 SFT 末尾漏加 `<\|im_end\|>` | Loss 正常收敛，无报错 | 回复结束后无限复读或自问自答永不停止 | 强校验首 Token 仅 1 个 BOS，每轮 Assistant 末位必为 EOT 且 `m_t = 1` |
| **2. 空格与换行边界错位** | 训练模板写 `assistant\n` 而推理框架多一个空格 `assistant \n` | 离线评估与训练口径一致时完全看不出 | 线上指令遵循暴跌、角色串台、格式乱套 | 训推强制共享同一份 Jinja2 `chat_template` 并做字符级双向往返单测 |
| **3. 特殊标签被 BPE 切碎** | 把 `<think>`、`<tool_call>` 当普通文本喂给分词器，被拆成 3–4 个碎片 Token | 仅在词表监控中可见微弱异常 | 工具调用解析失败、思考区闭合标签偶发拼错 | 所有控制符必须以 `additional_special_tokens` 注册并断言 `len(encode(tag)) == 1` |
| **4. 多模态占位符失配** | AnyRes 切片算出 1,280 patches，模板却硬编码填了 256 个 `<\|image_pad\|>` | 部分框架静默截断或广播特征，不抛异常 | 图像局部错位、多图张冠李戴、OCR 幻觉 | 预处理管线逐样本断言 `count(img_pad) == sum(T_img)` 且图像占位 `m_t = 0` |
| **5. <a class="term-ref" href="/books/llm-data/glossary#loss_mask" title="在多轮监督训练中精确区分模型主动生成的思考与动作（置 1）和用户输入、工具返回等环境观测（置 0）的逐 Token 梯度开关">Loss Mask</a> 误开或错移** | 忘记把 System / User / Tool Observation 掩码置 0；或 Shift-by-1 偏移 1 位 | Loss 更低（模型在背诵用户问题和 JSON 报错！） | 推理时抢答用户下一句话、自己伪造工具返回结果 | 抽样反解码打印彩色 Mask 视图（绿=1 / 灰=0）作为入库强制人工目检门禁 |

::: tip 黄金入库门禁：彩色反解码目检（Visual Token-Mask Inspection）
在把任何新语料（尤其是带 `<think>`、工具调用和多图交错的序列）送进千卡集群之前，**务必随机抽取 20 条打包后的最终 `input_ids`、`labels` 与 `position_ids` 张量**，逐 Token 反解码并用高亮颜色打印出每个 Token 的 ID、文本边界、Position ID 以及 `m_t` 掩码值。花 5 分钟肉眼扫过这 20 条终端输出，曾无数次帮顶级团队拦下价值数十万美元的静默模板事故。
:::

::: warning 严防长文本截断静默吞掉停止符与答案
当样本长度超出上下文上限（如 `max_len = 8,192`）而框架默认执行暴力右侧截断时，SFT / Long-CoT 样本末尾的 `</think>`、最终答案与 `<eot>` 会被直接切掉！如果大量长推理样本都在半路被截断却依然保留训练梯度，模型就会学到“写到一半突然卡住不收尾”的坏习惯。工程上对超出上限的 SFT/Agent 样本应采取**整条丢弃或路由至长窗桶**，绝不对半截残废推理链强行回传梯度。
:::
