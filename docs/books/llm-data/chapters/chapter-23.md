# 第 23 章 线上生产回流与端到端 Agent 数据飞轮

<p class="chapter-summary">打通从线上全链路 Tracing 到增量后训练的生产数据飞轮：挖掘覆盖全流量的显隐式失败信号，落地严防自测自训泄漏的“双轨物理隔离”架构，量化治理 API 与 UI 变更引发的 Agent 轨迹老化（Trajectory Staleness），并建立“更新数据 vs 改脚手架”的迭代 ROI 决策框架。</p>

离线合成再逼真，也很难提前穷举真实用户在生产环境里扔出的千奇百怪的长尾输入、脏格式附件与外部工具异常。真正具备复利效应的数据工程，必须让线上每一次用户交互、每一次工具报错与每一次人工兜底，都自动回流为下一代模型的养分。但生产回流也是一把双刃剑：**若缺少隔离防火墙，飞轮会迅速退化成“自测自训”的虚假涨点机器；若缺少老化治理，半年前的旧轨迹会把今天的 Agent 训成调用废弃接口的活化石**。本章拆解工业级生产飞轮的完整骨架与护栏。

## 23.1 生产全链路 Tracing：显式反馈与高量级隐式信号挖掘

生产飞轮的原料起点不是零散的对话文本，而是与第 15 章<a class="term-ref" href="/books/llm-data/glossary#trajectory_ir" title="跨工具调用、终端、检索与 GUI 的标准化多模态轨迹中间表示结构">统一轨迹中间表示（Trajectory IR）</a>同构的**全链路生产 Trace**。埋点契约必须无损捕获五类字段：完整渲染后的模型 I/O（含系统提示版本）、多模态附件与 GUI 截屏指针、每次工具调用的 `schema_hash` / 入参 / 原始回包 / 耗时 / 退出码、路由与环境元数据（模型版本、检索召回 ID），以及用户侧后续行为事件。

实战中，许多团队只盯着“点赞/点踩”按钮收集数据，很快陷入样本枯竭与严重幸存者偏差（真实生产中显式反馈率通常不足 **1%–3%**，且高度偏向极端情绪用户）。真正撑起数据飞轮规模的，是覆盖 **100% 生产流量**的**高量级隐式行为信号**：

| 信号类型 | 具体可观测行为指标 | 覆盖率 | 误报特征与清洗要点 | 最适配的数据转化去向 |
| --- | --- | --- | --- | --- |
| **显式：直接人工修订** | 用户直接编辑 AI 草案、修改代码补丁后提交（Human Edits） | 5%–25% | 极低误报；剔除纯格式排版微调 | 顶级 On-policy DPO 正负对与 SFT 金标 |
| **显式：点赞 / 点踩 / 工单评分** | 显式负评 + 附带文字原因 | 1%–3% | 样本稀疏、存在用户情绪偏差 | 补充人工 Open Coding 失败归因 |
| **隐式：短时重问 / 纠偏追问** | 60 秒内高度相似重问，或出现“不对/重来/你漏了…”语义 | 10%–20% | 需区分“用户改主意”与“模型答错” | 高优先级困难失败样本池 |
| **隐式：会话中途弃用 / 取消** | 生成中点击 Stop、连续空置放弃或未点击交付物即关闭 | 8%–18% | 需先剥离网络超时与高延迟取消 | 结合截断位置排查慢思考与跑题 |
| **隐式：人工接管（Takeover）** | 客服转人工坐席、运维中止 Agent 手动敲命令、审批驳回 | 5%–15% | 高业务损益信号，必查接管后人工动作 | 黄金<a class="term-ref" href="/books/llm-data/glossary#counterfactual_repair" title="定位失败轨迹首个偏航步并回滚修正动作的高效数据修复工艺">反事实修复</a>素材（人工接管即修正动作） |
| **隐式：工具报错尖峰与死循环** | 连续 $\ge 3$ 次同类 4xx/Schema 校验失败、重复调用相同工具 | 3%–10% | 必须先与下游服务 5xx `infra_error` 解耦 | 工具 Schema 改进或 Agent 错后自愈训练 |

### 弱信号融合优先级公式与脏日志解耦

单一隐式信号噪声较高（例如用户点击 Stop 可能是自己临时离开），工业管线通常构造**基础设施门控的多信号优先级分**，将海量原始 Trace 自动排序供后续主动学习消费：

$$
S_{\text{prio}}(\tau) \;=\; \mathbb{I}\big[\neg \text{infra\_error}(\tau)\big] \cdot \Big(\alpha_1\,\text{Edit}(\tau) + \alpha_2\,\text{Takeover}(\tau) + \alpha_3\,\text{ToolLoop}(\tau) + \alpha_4\,\text{Retry}(\tau)\Big) \cdot \big(1 + \beta\,u_{\text{novel}}(\tau)\big)
$$

其中 $\mathbb{I}[\neg \text{infra\_error}(\tau)]$ 是硬门控开关：凡下游 RPC 返回 HTTP 502/504、限流 429 或沙箱容器 OOM 导致的失败，一律直接置零并转入运维告警，**绝不混入模型失败聚类池**；$u_{\text{novel}}(\tau)$ 刻画该会话相对现有训练池的语义新颖度与不确定性，确保新发长尾痛点自动浮到最前排。

## 23.2 自动化回流飞轮与双轨物理隔离铁律

全链路 Trace 采集入湖后，自动化飞轮按五步流水线持续运转：**① 失败自动聚类**（结合错误码、隐式信号标签与向量语义聚类，识别高频新发痛点簇）→ **② 隐私脱敏与合规审查**（执行第 24 章全模态<a class="term-ref" href="/books/llm-data/glossary#pii_redaction" title="文本假名化、截图框级遮罩与声纹去标识的全模态隐私擦除管线">PII 脱敏</a>并核验客户数据授权标记）→ **③ 硬哈希双轨分流** → **④ 主动学习筛选与修复** → **⑤ 增量后训练与灰度发布**。

在这五步里，第 ③ 步是整套飞轮绝不可退让的生命线——**<a class="term-ref" href="/books/llm-data/glossary#dual_track_isolation" title="线上日志按用户/会话/任务哈希严格物理拆分为互不相交的评测黄金集轨与训练候选池轨，杜绝自测自训泄漏">双轨物理隔离（Dual-track Physical Isolation）</a>**。正如 [《LLM 与 Agent 评测》第 17 章](/books/llm-eval/chapters/chapter-17) 与 [第 20 章](/books/llm-eval/chapters/chapter-20) 反复警示的：如果今天把线上错题放进评测集，明天又顺手塞进微调池，离线分数就会变成毫无意义的过拟合幻觉。工业界标准做法是在 Trace 进入业务湖仓的**最上游网关**即执行确定性实体哈希分流（按 `hash(user_id / tenant_id / task_cluster) mod 100`）：

- **轨 A · 评测黄金集轨（固定 15%–20% 哈希桶）**：写入物理独立对象桶，对所有训练脚本与算法研发设为严格 IAM 只读/不可见；按 [《LLM 与 Agent 评测》第 17 章](/books/llm-eval/chapters/chapter-17) 流程滚动沉淀为回归集与密封 Holdout 发布闸门，仅向上游研发输出“剥离原题实体的抽象失败模式”。
- **轨 B · 训练候选池轨（其余 80%–85% 哈希桶）**：执行**主动学习优先级排序**——综合模型熵/多采样分歧度（不确定性）、对应失败簇的业务损益权重以及稀有长尾覆盖增益挑出高价值样本，再做人工/强模型反事实修复或同源合成，并与历史高质量锚点数据混配（防灾难性遗忘），驱动周级或双周级增量 SFT / DPO / RLVR。
- **跨轨去污防火墙**：每次轨 B 冻结新训练快照前，强制对轨 A 全部历史黄金题运行<a class="term-ref" href="/books/llm-data/glossary#decontamination" title="通过 N-gram 精确匹配与语义近邻检测剔除训测重叠样本">训练侧去污</a>（13-gram 精确重叠必须为 $0\%$，语义余弦相似度 $>0.90$ 自动拦截复核），杜绝不同用户问出高度雷同工单造成的隐性跨轨泄漏。

### 典型周级飞轮漏斗算例

以一个日均 15 万会话的企业 Agent 为例，单周回流漏斗的真实数量级如下：
1. **原始全量 Trace**：本周采集 **$1{,}050{,}000$ 条**会话；剔除健康无异动与 `infra_error` 后按硬哈希物理分流，**$15\%$（$157{,}500$ 条）**直入轨 A 供评测团队按聚类抽样扩容黄金集（每周净增 50–100 道高区分度新题）；
2. **轨 B 候选提纯**：剩余 **$892{,}500$ 条**中，隐式+显式信号命中潜在失败或人工修订约 **$71{,}400$ 条**（8.0%）；经脱敏、语义去重与失败聚类收敛为 **42 个高频失败簇**；
3. **主动学习与精修入库**：按“簇频次 × 业务损益 × 不确定性”截取前 **$3{,}000$ 条**最高杠杆轨迹（其中 1,200 条来自直接 Human Edits 免标入库，1,800 条经强模型反事实修复 + 沙箱终态断言通过），连同历史 12,000 条核心锚点数据冻结为本周增量快照，单周增量微调数据投入控制在数千美元量级。

## 23.3 飞轮护栏：分布漂移与轨迹老化（Trajectory Staleness）治理

纯文本问答数据的保质期往往长达数年，但**企业级 Agent 轨迹是极易腐烂的生鲜资产**。随着业务演进，后端 REST/MCP 接口增删字段、前端页面改版调整按钮布局、公司审批规章调整阈值，几个月前经过严格校验的“金牌历史轨迹”会在悄无声息间变成教模型调错参数、点偏坐标的毒药。我们将这一独特现象定义为**<a class="term-ref" href="/books/llm-data/glossary#trajectory_staleness" title="因线上工具 Schema 变更、UI 改版或业务规章更新导致历史 Agent 轨迹沦为过时错误示范的现象">轨迹老化（Trajectory Staleness）</a>**，并用可测量的**历史轨迹失效率 $\psi_{\text{stale}}(t)$** 进行量化监控：

$$
\psi_{\text{stale}}(t) \;=\; \frac{\big|\{\tau \in \mathcal{D}_{\text{hist}} : \mathrm{Replay}(\tau, \mathcal{E}_t) = \text{Fail} \;\lor\; \mathrm{SchemaHash}(\tau) \neq \mathrm{SchemaHash}_t\}\big|}{|\mathcal{D}_{\text{hist}}|}
$$

其中 $\mathcal{E}_t$ 为当前时刻 $t$ 的最新<a class="term-ref" href="/books/llm-data/glossary#environment_as_data" title="把可重置、带确定性断言的沙箱环境当作一等数据资产版本化管理的范式">沙箱环境</a>与工具契约集合。

**真实生产数值案例**：某企业 SaaS 运维与订单 Agent 在 9 个月内沉淀了 $40{,}000$ 条高质微调轨迹。期间业务侧上线 API v3（重构了 2 个核心查询接口入参）并改版了 3 个 Web 后台表单。某次例行增量微调未清理历史池，全量混训后线上工具调用一次成功率竟离奇暴跌 **9.4 个百分点**！事后对历史池做分层沙箱重放审计发现：$\psi_{\text{stale}}$ 已高达 **$27.5\%$**（$11{,}000$ 条旧轨迹在教模型输出已废弃的枚举参数和偏移 120 像素的旧按钮坐标）。

为此，成熟的数据飞轮必须按数据易变度建立**分层 TTL 与自动回放治理表**，并叠加在线分布漂移（PSI / 向量质心漂移）告警：

| 轨迹 / 资产类别 | 典型保质期（TTL） | 自动触发回放校验的条件 | 触发 $\psi_{\text{stale}} > 5\%$ 后的处置动作 |
| --- | --- | --- | --- |
| **通用领域知识与推理 QA** | 12–24 个月 | 季度规章修订或政策变更 | 标记过时文档源，增量替换为新版知识问答 |
| **稳定底层工具（SQL / Python / Bash）** | 6–12 个月 | 运行时/库大版本升级、表结构迁移 | 沙箱批量重跑单测，仅保留仍 Pass 的轨迹 |
| **业务 REST / MCP 工具轨迹** | **强绑定 `schema_hash`** | 上游接口发版（CI Webhook 自动触发） | 立即封存旧 `schema_hash` 分区，定向合成新版轨迹补血 |
| **高频改版 Web / Desktop GUI 轨迹** | **30–90 天** | 前端发布或页面视觉结构相似度突降 | 淘汰失效坐标轨迹，改用新页面 A11y Tree 逆向补采 |

### 在线分布漂移监控（Distribution Shift Telemetry）

除轨迹自身老化外，业务季节性波动（如大促、财报季）或新产品上线还会引发线上输入分布剧变。飞轮监控看板应按周计算线上意图聚类分布相对于当前训练集基线的**群体稳定性指标（PSI）**：

- **$\mathrm{PSI} < 0.10$**：线上分布稳定，维持常规双周增量迭代节拍；
- **$0.10 \le \mathrm{PSI} < 0.25$**：出现中度意图偏移，自动向新增长尾簇倾斜主动学习采样配额；
- **$\mathrm{PSI} \ge 0.25$**：发生显著业务跃迁，立即触发轨 A 黄金集专项扩容与轨 B 定向合成补血，防止旧基线模型在未知新场景大面积失灵。

## 23.4 飞轮迭代 ROI 决策框架：何时更新数据，何时先修脚手架？

建好了自动化回流飞轮，最忌讳陷入“拿着锤子看什么都像钉子”的误区——线上每冒出一个 Bad Case 就急着起一轮微调，不仅烧钱慢半拍，还会不断积累模型运维税。回流聚类出的每一簇线上问题，进入轨 B 训练队列前都必须先过一遍与 [《LLM 与 Agent 评测》第 20 章](/books/llm-eval/chapters/chapter-20) 完全咬合的 **ROI 决策路由表**：

| 线上失败簇的诊断特征 | 最优处置动作 | 响应周期 | 原因与成本逻辑 |
| --- | --- | --- | --- |
| 报错源于工具文档歧义、参数命名冲突、返回日志过长淹没核心字段 | **修脚手架 / 重写 MCP Schema**（绝不动数据） | 小时–1 天 | 零训卡成本、可瞬时灰度回滚，收益立竿见影 |
| 知识缺失、最新政策/价格变动、特定文档未入检索库 | **更新 RAG 知识库与多模态索引**（绝不用微调背事实） | 分钟–小时 | 易变事实写进权重必然过时且诱发幻觉 |
| 单一偶发长尾 Bug，周发生量 $< 0.2\%$ 且业务损益低 | **暂存观察池，不触发专项采标** | 异步累计 | 优先保证主力失败簇 ROI，避免小样本过拟合 |
| 脚手架干净后仍高频复现（周占比 $\ge 2\%$），$\widehat{\mathrm{pass@}8} - \widehat{\mathrm{pass@}1}$ 剪刀差大 | **启动轨 B 主动学习 + 增量 RLVR / 反事实修复 SFT** | 1–2 周 | 能力瓶颈在模型内化决策，数据飞轮边际收益最高 |
| 旗舰模型能稳过但线上推理账单过高、P95 延迟超标 | **轨 B 收集旗舰线上轨迹 → 离线蒸馏私有 8B–32B 小模型** | 2–3 周 | 只要日调用量足够大，1–3 个月内推理省费即可覆盖全套数据与训练投入 |

::: tip 飞轮启动的“最小可用节拍”（MVP Cadence）
切忌一上来就追求“全自动每小时在线学习”——无人监管的连续自动更新极易在一次上游接口故障或刷量攻击后彻底毒化模型权重。99% 的工业团队最佳实践是**“日志采集、聚类与脱敏全自动，快照审核与模型发布保留人工闸门”**，以**周级/双周级**的稳定节拍滚动迭代，并在每次上线前用轨 A 密封 Holdout 做统计显著性终审。
:::

::: warning 严防“飞轮正向偏置”导致的隐性萎缩
如果只把线上“失败样本”持续喂进微调池而不按比例混入“已做好的成功样本与通用能力锚点”，几轮飞轮转下来模型会出现严重的分布偏移——把新 Bug 修好了，却把原本最稳的主流场景训退化了。每轮增量快照中，新增线上纠偏样本的占比建议控制在 **10%–25%**，其余由经过老化体检的存量核心锚点与通用基准数据稳住底盘。
:::

当生产数据飞轮开始高速吞吐来自成千上万真实用户与多模态附件的日志时，任何一次隐私泄露、恶意提示注入或版权违规都可能让整个项目一夜停摆。下一章，我们系统构筑数据工程的底线防线——**全模态隐私脱敏、投毒与间接注入净化及版权合规治理**。
