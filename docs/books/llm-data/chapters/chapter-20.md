## 20.1 严酷去伪：识别与清除 Lucky Hacks、冗余死循环与格式退化

在多轮 Agent 合成与<a class="term-ref" href="/books/llm-data/glossary#rejection_sampling" title="对每题采样多条候选路径并经确定性验证器与高置信裁判筛选保留优胜样本的范式">拒绝采样</a>中，**“终态断言返回 True”只是入库必要条件，绝非充分条件**。只要验证环境存在哪怕一丝缝隙，模型在高并发探索中就会稳定产出占比 **$15\%\text{–}30\%$** 的<a class="term-ref" href="/books/llm-data/glossary#lucky_hack" title="虽侥幸触发通过判定但存在篡改单测、盲目瞎蒙或严重冗余的毒化轨迹">假成功 / 瞎蒙轨迹（Lucky Hack）</a>。如果不清除这些毒化轨迹，微调出的模型将系统性学会偷懒、作弊与无休止空转。

工业级轨迹净化流水线必须针对五类高频病灶设立自动化拦截闸门：

| 毒化轨迹病灶 | 典型表现特征 | 自动化检测与清除手段 | 放行后果 |
| --- | --- | --- | --- |
| **篡改测试 / 绕过验证** | 修改 `test_*.py` 断言、硬编码样例返回值、`sys.exit(0)` 或跳过权限校验 | 静态 Git Diff 禁止路径审计 + AST 特征扫描 + 隔离重跑只读验收脚本 | 模型彻底学会奖励黑客（Reward Hacking） |
| **盲目瞎蒙 / 暴力穷举** | 不读报错堆栈，连续猜 10 组随机参数或粘贴无关代码碰巧撞对 | 行为因果审计（校验每次修参是否引用前一步错误信号）+ 步效阈值拦截 | 推理链崩溃，线上泛化能力极差 |
| **冗余死循环空转** | 连续 $\ge 3$ 轮调用完全相同参数且报同错，或反复无意义翻页/回退 | 哈希重复动作滑动窗口检测；凡步数超同题成功中位数 **$2.5\times$** 直接剔除或剪枝 | 浪费线上推理 Token 与延迟，学会拖延 |
| **危险副作用越界** | 虽过窄断言但执行了 `chmod 777`、`rm -rf`、打印密钥或污染无关数据库表 | 系统调用/命令黑名单 + 全库/全目录 Diff 副作用零脏写审计 | 上线即引发严重安全与生产事故 |
| **思维-动作割裂与格式退化** | `<think>` 推理要删 A 文件，实际工具调用却改了 B；破损 JSON 靠容错解析蒙混过关 | 严格 JSON Schema 零容错重校验 + 轻量过程裁判抽查思行一致性与语言纯净度 | 工具调用解析崩坏、可解释性尽失 |

## 20.2 化废为宝：错误归因、反事实回滚修复与 Step-DPO / PRM 构造

假设你的任务池很有挑战性，当前策略端到端通过率只有 $\eta_{\text{pass}} = 20\%$。在传统拒绝采样下，另外 $80\%$ 的失败轨迹会被整批废弃——但打开日志仔细观察就会发现，其中超过一半的“中后程险败轨迹”前 10 步推理严丝合缝，仅仅因为第 11 步少看了一个报错字段或点偏了一个按钮才功亏一篑！

<a class="term-ref" href="/books/llm-data/glossary#counterfactual_repair" title="对失败轨迹定位首个关键偏航步并回滚沙箱注入专家修复动作以构造高质量正样本与步级对比对的技术">反事实修复（Counterfactual / Backtracking Repair）</a>正是把沉没失败算力转化为黄金资产的核心引擎：

<figure class="book-figure">
  <img src="/figures/llm-data/trajectory-filter-counterfactual.svg" alt="Agent 轨迹去伪过滤与失败反事实回滚修复构造 Step-DPO/PRM 对架构图" loading="lazy">
  <figcaption><span class="book-figure__label">图 20-1</span>左侧三道闸门清除表面通过池中的 Lucky Hacks；右侧对失败轨迹定位首个关键分叉点 s_t* 并利用 CoW 沙箱回滚注入专家修正动作，同步收获复活金轨与同前缀高信噪比 Step-DPO / PRM 对比对。</figcaption>
</figure>

整个反事实修复闭环包含四个精密工程步骤：
1. **自动化错误分类归因**：先由规则与诊断模型把失败轨迹归入五大根因——规划拆解缺失、UI/Schema 定位错误、工具报错误读、遗漏边界自检或步数耗尽，优先筛选“前置探索有效、失败集中于单一失误”的高潜险败样本。
2. **关键分叉步精准定位（Critical Divergence Step $t^\star$）**：利用强诊断模型结合终态失败日志（或对有快照的轨迹做二分采样探测），找出最早使任务从“仍可求解”滑向“死胡同”的那个分水岭步骤 $t^\star$。此时，前置轨迹 $\tau_{<t^\star}$ 是完全真实、同策略且有价值的探索历史。
3. **沙箱状态回滚与最小专家介入**：借助第 15 章可重置沙箱（CoW OverlayFS / SQLite / MicroVM 快照），毫秒级把环境恢复至进入状态 $s_{t^\star}$ 之前的精确切面；仅在 $t^\star$ 步调用更强教师模型（可附带失败反思提示“上次尝试 $a_{t^\star}^-$ 导致了如下报错，请改走正确路径”）或人工专家介入 **1–2 步**产出修复动作 $a_{t^\star}^+$；随后交还给**原目标策略自行续跑至终态通过**！
4. **原生零偏移构造 Step-DPO 与 PRM 样本**：反事实修复最惊艳的副产品，在于分叉点 $s_{t^\star}$ 天然构成了完美的<a class="term-ref" href="/books/llm-data/glossary#on_policy_preference" title="正负样本均由当前待优化策略本身采样产生并标注偏好的低偏移偏好数据集">同策略</a>步级对比对——共享完全一致的历史上下文 $\tau_{<t^\star}$，正样本是导向通关的 $a_{t^\star}^+$，负样本是当前策略真实犯下的错误 $a_{t^\star}^-$。将其直接代入 **Step-DPO** 步级偏好目标函数，即可精准把梯度集中到决定成败的那一步（同时也能以二元交叉熵训练步级过程奖励模型 Step-PRM）：

$$
\mathcal{L}_{\text{Step-DPO}}(\theta) = -\,\mathbb{E}_{(\tau_{<t^\star},\, a_{t^\star}^+,\, a_{t^\star}^-)} \left[\log \sigma\!\left(\beta \log \frac{\pi_\theta(a_{t^\star}^+ \mid \tau_{<t^\star})}{\pi_{\text{ref}}(a_{t^\star}^+ \mid \tau_{<t^\star})} - \beta \log \frac{\pi_\theta(a_{t^\star}^- \mid \tau_{<t^\star})}{\pi_{\text{ref}}(a_{t^\star}^- \mid \tau_{<t^\star})}\right)\right]
$$

相比整条长轨迹粗粒度偏好对比，步级对比把信用分配精确锁定到单步决策分水岭，彻底消除“前面十步好动作因最后一步失误被连坐惩罚”的梯度方差。

### 修复 ROI 数值账本：为什么反事实修复比盲目重跑划算得多？

假设一批 10,000 道高难多轮任务，目标策略初次 Rollout 单次综合成本 $C_{\text{roll}} = \$0.11$（含生成与沙箱），初始净通过率 $\eta_0 = 20\%$（得 2,000 条正轨，单轨成本 $C_{\text{eff}}^{(0)} = 0.11 / 0.20 = \mathbf{\$0.55}$）。此时若对 8,000 条失败轨迹中筛选出的 $40\%$ 中后程险败样本（3,200 条）实施反事实回滚修复（定位归因 + 强教师 1.5 步纠偏 + 后半程续跑平均成本 $\$0.12 / \text{条}$，修复通关率 $75\%$）：
- **新增复活金轨**：$3{,}200 \times 75\% = \mathbf{2{,}400}$ 条，总有效金轨从 2,000 飙升至 **4,400 条**，等效总留存率从 $20.0\%$ 跃升至 **$44.0\%$（$2.2\times$）**！
- **单位有效成本骤降**：总支出 $10{,}000 \times 0.11 + 3{,}200 \times 0.12 = \$1{,}484$，摊薄到 4,400 条金轨后单价降至 $C_{\text{eff}}^{(1)} = \mathbf{\$0.337 / \text{条}}$（**直降 $38.7\%$**），并且**零额外边际成本免费获赠 2,400 组精准的 Step-DPO / PRM 步级偏好对**！

## 20.3 长程上下文压缩（Context Compaction）与跨会话长期记忆数据

真实企业级 Agent 往往要连续执行 50–200 步操作（如跨周推进一个大型代码重构或长期跟进客户项目），上下文窗口很快被海量中间工具输出塞满，既引发推理延迟飙升，又触发“中间迷失（Lost in the Middle）”注意力退化。要突破单会话短视窗瓶颈，必须专门合成两类高阶长程记忆数据：

### 1. 以“续跑通关率”验真的上下文压缩摘要工厂

<a class="term-ref" href="/books/llm-data/glossary#context_compaction" title="当长程交互逼近上下文上限时将早期冗余工具日志压缩为高保真结构化状态摘要的专用能力与数据">上下文压缩摘要（Context Compaction）</a>数据绝不能用传统的 ROUGE 或主观流畅度来筛——摘要写得再优雅，只要漏掉了一个报错行号或已修改的配置文件名，后续执行就会全盘皆输。工业级构造方法采用**下游续跑无损验真（Continuation Parity Verification）**：
- 从 Tier 2 超长成功轨迹（如 40K tokens、35 轮）的中间切点（如第 20 轮）切开，让摘要模型将前 20 轮浓缩为 **1.5K–3K tokens 的结构化工作记忆**（强制包含四栏：已证实关键事实与证据指针、已变更文件/数据库状态、已排除死胡同、剩余待办约束）；
- 将原前 20 轮完整替换为该压缩摘要，放回沙箱让目标策略续跑剩余任务；**仅保留续跑仍稳定通过终态断言且压缩比达 $8\times\text{–}20\times$、延续通关率保持 $\ge 95\%$ 的无损压缩样本**。典型工业级结构化压缩契约必须固定保留以下四类不可丢失的状态字段（将 $40{,}000$ tokens 压至 $\sim 1{,}800$ tokens，压缩比 **$22.2\times$**）：

```json
{
  "verified_facts": ["src/pool.py:84 连接超时硬编码为 5s", "pytest test_retry.py 稳定复现超时"],
  "state_mutations": ["已编辑 src/pool.py（支持读 env TIMEOUT）", "未触碰 migrations/"],
  "eliminated_hypotheses": ["已排除 DNS 解析延迟（dig 耗时 1.2ms）"],
  "open_constraints": ["须补全超时边界单测", "提交前运行全量回归并删除 tmp_repro.py"]
}
```

同时构造“主策略识别窗口逼近阈值后主动调用 `compact_context` 工具”的边界触发样本。

### 2. 跨会话长期记忆 CRUD 演进数据

跨天、跨周陪伴用户的个人或企业 Agent，不能每次开新会话都“失忆重来”，更不能把过时旧偏好死板拼接在一起。数据工厂通过模拟同一用户在 5–10 个跨周会话（Session 1 $\to$ Session $K$）中的演进时间线，系统覆盖长期记忆的四大原子操作：
- **Write（选择性沉淀）**：辨别持久事实（如“生产库使用 UTC 时区、报告偏好表格优先”）与一次性临时寒暄，避免记忆库被垃圾撑爆；
- **Read（抗干扰召回）**：在塞满几十条语义相近干扰记忆的向量/键值库中，精准检索当前任务真正依赖的历史约束；
- **Update（时序冲突覆盖）**：核心难点！例如 Session 1 用户定下用 PostgreSQL，Session 3 明确拍板迁移至 ClickHouse；训练轨迹必须演示显式覆盖或将旧条目置为 `superseded`，杜绝 Session 5 答复时把新旧架构混为一谈；
- **Forget（过期与合规遗忘）**：当用户要求“忘掉我上次提供的身份证号/临时项目代号”或记忆触及 TTL 时，准确触发删除工具，并在后续探针会话中验证彻底不再复述。

## 20.4 多智能体协作（Multi-Agent）轨迹数据：委派、冲突消解与汇总结论

当单一任务同时跨越大规模代码检索、并行模块改写、独立安全审查与深度资料调研时，单智能体串行循环既慢又容易被海量局部细节污染主上下文。衔接[《LLM 强化学习》第 15 章](/books/llm-rl/chapters/chapter-15)的 Agentic 与多智能体后训练框架，多智能体协作能力同样需要专门构建高质量协作轨迹数据，绝不能靠单智能体轨迹自然“涌现”。

多智能体数据工厂重点沉淀四类高杠杆协作原型与一项核心掩码铁律：
1. **Planner–Worker 自包含派单委派**：最常见的多智能体失效不是子 Agent 笨，而是编排者下达了充满隐含指代的糟糕任务书（如“帮我修一下刚才那个模块”）。优质样本必须示范 Planner 将大任务拆解为边界清晰、无写冲突的并行子任务，并为每个 Worker 编写**完全自包含的 Brief**（显式路径、接口契约、验收标准与禁止越界范围）。
2. **独立对抗审查与定向返工（Reviewer–Worker Loop）**：引入只读视角的审查者/测试者 Agent，对着 Worker 提交的 Diff 或研究报告执行逐条<a class="term-ref" href="/books/llm-data/glossary#rubric" title="将开放式任务拆解为可核验、带权重的原子检查项与扣分红线的数据资产">Rubric</a> 缺陷挑刺，产出结构化缺陷单；再由 Worker 精准修复，直至通过终态断言且无无休止“踢皮球”循环。
3. **多路冲突仲裁与状态汇合**：当 Worker A 与 Worker B 返回相互矛盾的调研数据或修改了重叠代码文件时，专门构造 Planner 基于一手证据权重或运行集成测试完成仲裁合并的轨迹，杜绝“各打五十大板”的敷衍折中。
4. **角色专属非对称<a class="term-ref" href="/books/llm-data/glossary#loss_mask" title="在多轮 Agent 监督训练中精确区分模型动作置 1 与外部环境观测置 0 的逐 Token 梯度开关">Loss Mask</a>隔离**：在多智能体<a class="term-ref" href="/books/llm-data/glossary#trajectory_ir" title="跨工具调用、终端执行、网页检索与 GUI 操控的标准化 JSON/Parquet 轨迹数据结构">Trajectory IR</a> 渲染训练序列时，**同一条协作图谱必须按待训练角色拆分视角并执行严格非对称掩码**，严防“编排者自演子智能体回复”或“执行者遇事不干活只会无限再转包”的回音室怪胎。各角色的 Token 掩码矩阵如下：

| 轨迹消息类型 | 训练 Planner 编排权重时 ($m_t$) | 训练 Worker 执行权重时 ($m_t$) | 训练 Reviewer 审查权重时 ($m_t$) |
| --- | --- | --- | --- |
| **用户原始任务与系统提示** | `0`（仅作条件上下文） | `0`（或仅见父节点 Brief） | `0`（仅见验收 Rubric 与交付物） |
| **Planner 思考、拆解与派单 Brief** | **`1`**（核心编排梯度） | `0`（视作外部输入指令） | `0`（视作任务背景上下文） |
| **Worker 局部工具循环与交付返回** | `0`（严格视作工具观测） | **`1`**（局部思考/动作/EOS） | `0`（待审查的外部输入对象） |
| **Reviewer 缺陷审计与驳回清单** | `0`（视作外部审查反馈） | `0`（视作返工纠错观测） | **`1`**（核心核验批评梯度） |
| **Planner 冲突仲裁与最终汇总答复** | **`1`**（核心决策汇合梯度） | 不可见（不在子上下文） | 不可见（不在子上下文） |

## 20.5 第五篇总收束：Agent 全栈数据资产与准入总账

回顾第 15–20 章，我们完整构建了横跨四大垂直业务与两大高阶前沿的 Agent 数据工程全栈。下表收束全篇各工厂的核心真值锚点、目标留存口径与头号避坑红线：

| 章节与垂直工厂 | 核心真值验证锚点 | 目标有效留存 $\eta_{\text{pass}}$ | 单位有效轨迹单价 $C_{\text{eff}}$ | 头号工程失控陷阱 |

::: tip Step-Level 对比信号是打破 Agent 能力瓶颈的最高效杠杆
大量工业消融反复印证一条规律：当 SFT 轨迹池达到数万条高纯度 Tier 2 规模后，继续单纯堆叠同分布正样本的边际收益会迅速放缓；此时，利用 20.2 节反事实修复产出的同前缀 **Step-DPO 对比对**或 **Step-PRM 引导的 RLVR** 仅需训练 1–2 个 Epoch，就能在复杂多轮纠错、边界遵守与长程收敛率上带来相当于翻倍 SFT 数据量 **$2\times\text{–}4\times$** 的跃升。
:::

::: warning 警惕无外部锚定的“自产自销”合成陷阱
无论是工具仿真、逆向 GUI 任务还是多智能体协同，如果整个工厂只靠大模型自己出题、自己打分、自己扮演环境、自己收割轨迹循环训练，几轮迭代后必然会坠入<a class="term-ref" href="/books/llm-data/glossary#model_collapse" title="模型反复在缺乏真实世界锚定或外部验证的自身合成数据上递归训练导致分布尾部消失、输出僵化的退化现象">模型坍缩</a>——轨迹越写越像死板八股文，遇到真实线上脏输入立刻崩溃。**必须始终锚定真实环境真值（编译器、数据库、OS 状态、一手文档）与线上生产回流数据**。
:::
