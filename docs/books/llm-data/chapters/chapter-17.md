# 第 17 章 Coding / SWE 与终端运维 Agent 数据工厂

<p class="chapter-summary">解剖仓库级 SWE 任务挖掘与容器化环境构建的严酷留存漏斗，深入 SWE-smith / SWE-gym 镜像复用与 AST 缺陷注入、F2P/P2P 单测合成及 Linux 终端运维故障工厂，并算清长程多文件编辑轨迹剪枝与存储算力经济账。</p>

在所有 Agent 垂直领域中，软件工程（SWE）与 Linux 终端运维拥有全行业最硬核的真值信号——编译器报错、单元测试套件、进程状态与服务健康探针几乎零主观争议，使其成为 SFT 拒绝采样与<a class="term-ref" href="/books/llm-data/glossary#rlvr_data" title="由清晰难题 Prompt 与抗作弊确定性验证器成对构成的可验证奖励强化学习数据资产">可验证奖励强化学习（RLVR）</a>的天然练兵场。然而，真正动手搭建过 SWE 数据工厂的团队都深有体会：**写代码难的从来不是找 GitHub 仓库，而是让几万个历史 Commit 在隔离容器里“一键跑通测试且绝不抖动”**。本章从自然挖掘的现实瓶颈出发，系统展开面向十万级任务规模的容器复用与可验证合成工厂。

## 17.1 仓库级 SWE 任务挖掘与容器化环境构建漏斗

遵循经典 SWE-bench 范式从开源社区挖掘真实仓库级修复任务，标准流水线包含四步：开源协议与活跃度初筛 $\to$ 关联 Issue 与已合并 PR 配对 $\to$ 将 PR Diff 物理拆分为 `code_patch`（源码修改）与 `test_patch`（测试修改） $\to$ 自动化依赖解析与 Docker/MicroVM 镜像构建。同时，在最上游必须执行严格的<a class="term-ref" href="/books/llm-data/glossary#decontamination" title="通过 N-gram、后缀数组或语义检索主动剔除与公开或密封评测集重叠样本的清洗机制">训练侧去污</a>：不仅剔除 SWE-bench / SWE-bench Verified / Live 等基准中的全部评测 Issue ID，更应按仓库维度或严格的时间戳截断隔离，杜绝同仓近邻 Commit 泄漏。

然而，当把这套自然挖掘管线放到十万级 PR 上真实跑一遍时，你会看到一张令人警醒的<a class="term-ref" href="/books/llm-data/glossary#yield_funnel" title="原始数据经过多层解析、过滤、构建与验证后最终进入训练集的留存漏斗">数据留存漏斗</a>账本：

| 挖掘与构建漏斗阶段 | 核心自动化步骤与筛选口径 | 阶段留存率 | 剩余任务数 | 累计留存 $\eta_{\text{yield}}$ |
| --- | --- | --- | --- | --- |
| **0. 原始合并 PR 池** | 多语言主流开源仓（Python/TS/Go/Rust/Java）已合并 PR | $100.0\%$ | 100,000 | $100.0\%$ |
| **1. Issue + 测试补丁配对** | 明确绑定问题描述且 Diff 同时改动源码与测试文件 | $18.0\%$ | 18,000 | $18.0\%$ |
| **2. 合规、体量与去污过滤** | 宽松许可证、非纯文档/锁定文件改动、剔除基准重叠仓 | $55.0\%$ | 9,900 | $9.90\%$ |
| **3. 自动化容器镜像构建** | 锁文件解析 + LLM 修复 Agent 调通 Dockerfile，基线测试可运行 | $46.0\%$ | 4,554 | $4.55\%$ |
| **4. 严格 F2P / P2P 3× 防抖验真** | 满足<a class="term-ref" href="/books/llm-data/glossary#fail_to_pass" title="应用补丁前稳定失败、应用正确补丁后稳定通过且不破坏已有测试的验收标准">失败转通过（Fail-to-Pass）</a>且连跑 3 次结果零漂移 | $52.0\%$ | **2,368** | **$2.37\%$** |

端到端留存率仅有 **$2.37\%$**！更致命的是容器存储与冷启成本：不同历史 Commit 往往依赖不同版本的 C 扩展、GCC/LLVM 或 Python 轮子，几乎退化为“1 个镜像只服务 1.2 道题”。若想靠自然挖掘攒够 20,000 道题，光未压缩 Docker 镜像层就会吞噬超过 **50 TB** 存储，拉取镜像成为集群并发的最大卡点。

## 17.2 规模化可验证任务合成：AST 缺陷注入与 F2P/P2P 单测工厂

既然“把环境配通”是最昂贵的瓶颈，工业界（以 SWE-smith、SWE-gym 为代表）彻底反转了生产顺序——从“先找题再拼命配环境”转向**“先建好 1 个健康可运行的仓库基线镜像，再在同一个镜像里规模化合成 50–200 道自带确定性验证的任务”**。这正是第 15 章<a class="term-ref" href="/books/llm-data/glossary#environment_as_data" title="把可重置、可并发实例化、带确定性状态断言的沙箱应用/数据库/代码仓本身当作一等数据资产来规模化生产和管理">环境即数据</a>在软件工程领域的巅峰体现。

在一个基线测试全绿、且支持 Copy-on-Write（CoW）OverlayFS 40ms 秒级重置的仓库容器上，数据工厂可并行驱动四类高可信任务合成算子：

1. **AST 与依赖图引导的缺陷注入（Bug Injection）**：绝非随机删行，而是先解析仓库抽象语法树（AST）与跨文件调用图，定向对核心业务函数实施高保真语义变异——包括边界条件偏移（`<` 改 `<=`）、并发锁缺失或死锁序、异常吞没/错误码错位、缓存失效逻辑破坏、以及跨模块接口参数错配；也可以由强模型参考真实 Issue 风格注入隐蔽的逻辑缺陷。随后立即在容器内跑原仓库测试套件：**只要原全绿测试中稳定挂掉 $1\text{–}15$ 个用例、其余上百个用例保持全绿，这组挂掉的用例立刻成为天然无懈可击的 F2P 判据，而原健康源码本身就是 100% 正确的参考补丁！**再由强模型根据“故障现象 + 失败测试日志（屏蔽修复源码）”反写出逼真的用户 Bug Report 即可。
2. **历史提交逆向回滚与多文件重构合成**：在健康主干上精准定位不破坏依赖环境的近期功能 Commit，逆向应用 `git revert` 并保留对应测试，瞬间产出新特性实现与跨文件 API 迁移任务。
3. **自动化 F2P / P2P 单元测试合成**：针对大量只有文字 Bug Report 却缺回归测试的真实 Issue，以及无现成单测覆盖的深层模块，用专门的测试合成 Agent 先在“缺陷基线 $\times$ 修复参考补丁”双版本镜像上反复迭代编写测试脚本，并强制通过**变异测试校验（Mutation Check）**——确保新测试在缺陷版必挂、在修复版必过、在无关错误补丁上不空过，杜绝只会 `assert True` 的废测试。
4. **Linux 终端与 DevOps 故障排错工厂**：将同样范式延伸至非应用代码开发场景。在预装 Nginx、PostgreSQL、Redis、Systemd、Docker-in-Docker 或 Python/C++ 构建链的轻量容器/MicroVM 中，由故障注入脚本系统性制造真实线上事故——端口占用冲突、配置文件语法暗伤、文件权限/软链损坏、共享库 `LD_LIBRARY_PATH` 错配、磁盘 inode 耗尽、cgroup 内存 OOM 误配或慢 SQL 死锁；再配对黑盒终态健康断言（目标端口 `curl` 返回预期 JSON、服务存活、错误日志清零且持久化业务数据完好无损），规模化锻造终端运维排障能力。

下表归纳了工程实战中收益最高的六类 SWE 与终端运维合成算子及其确定性验收机制：

| 合成算子类型 | 具体故障 / 任务构造手段 | 确定性真值验证器 | 典型解决步数 |
| --- | --- | --- | --- |
| **AST 边界与状态变异** | 修改循环上下界、空值判据、锁释放顺序与状态机分支 | 原仓库测试套件中自然挂掉的 F2P 子集 + 全量 P2P | 12–28 轮 |
| **跨文件接口签名破坏** | 调整核心函数参数序或返回结构，遗留部分调用方未同步 | 静态类型检查（`mypy`/`tsc`）+ 集成测试套件 | 18–35 轮 |
| **PR 逆向功能回滚** | 在健康主干对完整 Feature Commit 执行逆向补丁 | 原提交配套单元测试 + 回归测试套件 | 25–50 轮 |
| **缺测 Issue 回归合成** | 针对纯文字 Bug 报告由双版本容器迭代生成回归单测 | 变异测试校验（缺陷版必挂、修复版必过、防空过） | 15–30 轮 |
| **Linux 服务与网络排障** | 注入 Nginx 配置语法错、端口占用、TLS 证书路径/权限错误 | `systemctl is-active` + `curl` 状态码/响应体 + 零报错日志 | 10–25 轮 |
| **编译链与数据库运维** | 破坏 `CMake`/Python venv 路径、SQLite/PG 索引锁与连接池上限 | 洁净编译产物校验 + 并发压测延迟与数据完整断言 | 15–35 轮 |

下面是一个典型的容器化终端运维任务黑盒验收契约示例——严禁仅检查进程是否在跑，必须同时校验对外业务响应与数据完整性：

```bash
# 终端运维终态断言脚本（在只读评测侧运行，Agent 不可见且不可修改）
set -euo pipefail
systemctl is-active --quiet nginx && systemctl is-active --quiet app-api
curl -fsS --max-time 3 http://127.0.0.1:8080/healthz | grep -q '"db":"ok"'
sqlite3 /var/lib/app/prod.db "PRAGMA integrity_check;" | grep -qx "ok"
test "$(sqlite3 /var/lib/app/prod.db 'SELECT COUNT(*) FROM orders;')" -eq 12480
```

## 17.3 长程多文件编辑轨迹采集与工程剪枝

有了十万级可验证任务后，还需把模型在容器里的真实操作锤炼成高质量长程轨迹。一条优秀的 SWE / 终端运维轨迹通常跨越 **20–60 轮**，呈现出清晰的专业工程师工作流：

1. **仓库侦察与符号定位**：先用 `rg`、`fd` 或 AST 符号大纲工具迅速锁定相关模块与调用链，而非盲目 `cat` 整份千行文件撑爆上下文。
2. **最小复现脚本构造**：动手改源码前，先在沙箱内编写并运行独立复现脚本，眼见为实确认故障触发路径。
3. **跨文件精准手术编辑**：采用行号锚定或精确上下文匹配的 `str_replace` / Unified Diff 补丁工具修改多处关联文件，避免整文件覆写引发的截断与误删。
4. **测试驱动调试与自检收敛**：运行局部与全量回归测试，若报错则读取堆栈调整假设，最后执行 `git diff` 清理临时调试脚本与冗余打印，确认零副作用后提交。

### 轨迹剪枝策略与工程留存标准

直接把所有通过 F2P/P2P 验收的原始轨迹塞进 SFT，会让模型学到大量低效试探习惯。工业级 SWE 数据工厂对通过轨迹实施四项标准化工程剪枝与课程筛选：

| 轨迹处理算子 | 适用触发条件 | 具体工程动作 | 保留 / 淘汰原则 |
| --- | --- | --- | --- |
| **超长日志关键帧折叠** | 单次 `pytest`/`gcc` 输出 $> 4\text{ KB}$ | 保留首尾摘要与首个 `AssertionError` 堆栈帧，折叠中间重复行 | 严禁直接截断末尾汇总导致模型看不到错误码 |
| **有效假设回滚保留** | 试错后主动 `git checkout` 并切换根因分析 | 完整保留诊断转向与回滚步骤（约占训练集 $15\%\text{–}20\%$） | 培养真实排障纠错元认知，避免只学“一发命中”脆性路径 |
| **空转死循环淘汰** | 同一语法错误连改 $\ge 4$ 轮或反复 `ls` 空转 | 整条剔除或送入第 20 章反事实修复引擎在分叉步重写 | 防止模型习得拖延刷步数与盲目碰运气 |
| **临时文件污染拦截** | 终态 `git status` 残留 `repro.py`/日志垃圾 | 要求模型收尾自清，或仅保留干净 Diff 的合格轨迹 | 确保交付补丁符合真实企业代码评审（CR）规范 |

- **甜点区难度分桶（Sweet Spot Curriculum）**：借助第 10 章的<a class="term-ref" href="/books/llm-data/glossary#sweet_spot_curriculum" title="根据当前模型采样通过率动态筛选中等难度题目的数据调度机制">甜点区动态课程</a>口径，用基座策略对每道合成题执行 $k = 8$ 轮采样估算通过率 $p_i$。套用[核心公式与数据账本速查卡](/books/llm-data/toolkit/formulas-and-ledgers)的组采样零梯度概率公式 $P(\text{zero-grad} \mid p_i, G) = p_i^G + (1 - p_i)^G$（取 $G = 8$）：
  - 若题库充斥极难题（$p_i = 0.05$），单步 Rollout 出现全错零梯度的概率高达 $0.95^8 \approx \mathbf{66.3\%}$，三分之二的昂贵容器算力白白空转；
  - 若题库被送分题淹没（$p_i = 0.95$），全对零梯度浪费同样高达 **$66.3\%$**；
  - 若严格将题池控制在 **$p_i \in [0.15, 0.80]$** 甜点区（例如 $p_i = 0.35$ 时零梯度概率骤降至 $0.35^8 + 0.65^8 = \mathbf{3.2\%}$），有效策略梯度利用率立刻稳定在 **$80\%\text{–}97\%$**！而对 $p_i < 0.10$ 的高难硬骨头，则转交强教师模型拒绝采样与第 20 章的反事实修复，避免在在线 RLVR 中直接空耗算力。

## 17.4 算力与存储经济账：自然挖掘 vs 镜像复用合成

为了直观呈现“环境即数据”在 SWE 工厂中的巨大财务杠杆，我们以产出 **20,000 条 Tier 2 可验证 SWE 有效轨迹**为目标，按教材统一口径横向核算两种路线的总拥有成本（设单条 30 轮轨迹推理费 $C_{\text{gen}} = \$0.032$、端到端通过率均按 $\eta_{\text{pass}} = 22\%$ 计）：

| 经济账维度 | 轨 A：纯自然 PR 挖掘路线 | 轨 B：基线镜像复用合成路线 | 工程增益倍数 |
| --- | --- | --- | --- |
| **所需独立容器镜像数** | ~16,700 个（1 镜约 1.2 题） | **~250 个**（1 镜摊销 80 题） | 镜像维护量直降 **$67\times$** |
| **镜像存储总占压** | ~50 TB（大量重复底层依赖） | **~1.2 TB**（CoW 共享基线层） | 存储与拉取带宽压降 **$40\times$** |
| **单次 Rollout 摊销环境与构建费 $C_{\text{env}}$** | $\$0.105$（含大量构建失败沉没成本） | **$\$0.008$**（40ms OverlayFS 重置） | 环境费直降 **$13\times$** |
| **单条有效轨迹综合成本 $C_{\text{eff}}$**（含校验） | $(0.032+0.105+0.004)/0.22 \approx \mathbf{\$0.64}$ | $(0.032+0.008+0.002)/0.22 \approx \mathbf{\$0.19}$ | 单位有效轨迹降本 **$3.4\times$** |
| **20,000 条轨迹总研发支出** | **$\$12{,}800$** + 数月人工修镜像 | **$\$3{,}800$** + 天级弹性扩容 | 可持续支撑百万级课程演进 |

工程上最佳配方是**“自然 PR 压舱（20%–30%）+ 镜像复用合成扩量（70%–80%）”**：前者锚定最真实的社区需求表述与复杂历史演进分布，后者以极低边际成本将代码语言覆盖度、跨文件深度与终端运维长尾故障推向规模化。

::: tip SWE 沙箱抗作弊加固红线（杜绝“偷看答案”式 Lucky Hack）
如果不对代码沙箱做彻底隔离，聪明的大模型会在几百步 RLVR 探索里迅速学会各种匪夷所思的<a class="term-ref" href="/books/llm-data/glossary#lucky_hack" title="虽侥幸触发通过判定但存在篡改单测、盲目瞎蒙或严重冗余的毒化轨迹">作弊捷径</a>：例如运行 `git log --all` 或 `git reflog` 直接捞出未来修复提交、通过外网 `curl` 查 GitHub 原 PR、或者直接把 `tests/` 里的断言删掉让 `pytest` 返回 0。每台 SWE 沙箱启动前必须强制执行四条硬命令：① 彻底删除修复后的 Git 对象并重建单提交干净仓库（`git init` 抹去历史与 remote URL）；② 容器以 `--network=none` 断网运行；③ 验收阶段始终在干净副本上重新 `git apply` 评测侧只读保存的 `test_patch`，绝不信任容器内可能被 Agent 改过的测试文件；④ 对补丁 diff 扫描禁止触碰的路径白名单。
:::

::: warning 隐形毒药：Flaky Tests（抖动测试）会系统性毒化 SFT 与 RLVR
哪怕题库中只有 $5\%$ 的测试受系统时间、多线程竞态、随机端口或临时文件残留影响而偶发抖动，在拒绝采样阶段就会把大量根本没修对 Bug 的错误补丁当成正样本混进训练集，在 RLVR 阶段更会把原本正确的策略打上负优势惩罚。任何任务入库前必须经过“固定 `TZ=UTC` + 独立空容器连续运行 3 次全一致”的防抖验真，凡出现一次不一致即刻隔离淘汰。
:::

攻克了编译与单测驱动的代码及运维世界后，下一章我们将走向另一片广阔却截然不同的疆域——没有现成 0/1 编译器裁判的 Deep Research、多模态企业 RAG 与知识工作流 Agent 数据工程。
