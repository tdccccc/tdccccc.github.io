# 第 17 章 评测驱动开发（EDD）：从零构建业务黄金评测集

<p class="chapter-summary">为什么公开榜单救不了你的真实业务？本章建立评测驱动开发（EDD）工作流，系统拆解“线上日志挖掘 → 能力×风险矩阵 → 专家联合标注与 Rubrics 细化 → 对抗样本合成与过筛 → 语义化版本冻结与周期轮换”五步黄金评测集落地流水线。</p>

很多大模型应用团队都经历过同一种挫败：底座从 A 模型换成 B 模型，公开榜单（MMLU-Pro、SWE-bench Verified、$\tau^2$-bench）全面领先 5–10 个百分点，上线后客服工单一次解决率却原地踏步，甚至在几个关键业务条款上频频犯错。原因并不神秘——公开榜单测的是通用能力的公约数，而企业产品成败取决于私有语料、业务政策、工具接口与成本红线的交集。

公开基准最多帮你把候选底座从二十个缩窄到两三个；真正驱动产品从 60 分稳定迭代到 95 分的，必须是贴着自身业务痛点长出来的私有黄金评测集。本章正式引入<strong><a class="term-ref" href="/books/llm-eval/glossary#edd" title="EDD，评测驱动开发：将业务黄金评测集与通过门槛置于开发之前的工程范式">评测驱动开发（EDD）</a></strong>，把“先立标尺、再改系统”固化为团队的日常工程纪律。

## 17.1 为什么公开榜单不能替代业务黄金集：EDD 范式确立

公开基准与企业真实生产之间横亘着三条无法靠“榜单加权平均”填平的鸿沟：

1. **分布与政策错位**：企业文档充斥内部缩写、历史修订条款、非标准表格与严格的权限边界，这些私域知识既不在预训练语料里，也无法用公开通用题近似；
2. **多轮状态与工具耦合**：公开问答多为单轮自洽，而企业业务强依赖专有 API、遗留数据库与多轮信息补齐，失败往往发生在工具参数校验、字段映射或状态回滚环节；
3. **风险函数极端不对称**：公开榜单上每道题等权记 1 分，但企业里“普通话术稍显啰嗦”与“越权给用户多退一万元”的业务代价相差五个数量级。

<strong>评测驱动开发（Evaluation-Driven Development，EDD）</strong>借鉴软件工程测试驱动开发（TDD）的核心哲学，但在大模型随机性与开放输出场景下做了三项关键适配：
- **先建标尺再动代码**：在动笔调 Prompt、搭脚手架或微调权重前，先冻结第一版业务黄金集（哪怕只有 50 道高质量种子题）并跑出可复现基线；
- **以误差归因为修改输入**：每一轮改动必须源自对失败样本的 <a class="term-ref" href="/books/llm-eval/glossary#open_coding" title="Open Coding，开放编码误差分析：人工通读真实失败轨迹并自下而上提炼根因分类表">Open Coding 误差分析</a>（第 16 章），而非研发或产品经理的“体感猜测”；
- **以统计显著性与红线为准绳**：任何优化必须通过配对检验与 <a class="term-ref" href="/books/llm-eval/glossary#mde" title="MDE，最小可检测效应：给定题量与功效下可稳定测出的最小真实分差">MDE</a> 门槛，绝不放行“只修好了演示 Demo 却弄坏隐性回归”的变更。

## 17.2 五步流水线：从零构建高信噪比业务黄金集

一套能抗住半年以上高频迭代、既不流于形式又不被团队过拟合的业务黄金评测集，需要按以下五步严格落地。

### 步骤一：真实线上日志与客诉 Bad Case 挖掘（去敏、去重与分层抽样）

黄金集的第一大忌，是关在会议室里由算法工程师凭空“编题”——工程师编出的题往往措辞规范、逻辑干净，与真实用户充满错别字、省略主语、情绪焦躁的输入相去甚远。

- **冷启动 vs 温启动**：产品未上线时，先从历史客服工单、人工问答库、SOP 手册与内部试用记录提取 50–80 条种子样本；产品一旦上线，真实交互日志、人工转接记录与客诉 Bad Case 就是最高纯度的金矿。
- <strong>结构保真脱敏（Structure-Preserving PII Redaction）</strong>：采用正则 + NER 管线替换姓名、手机号、证件号、订单号、内部密钥与真实金额，但必须**保留格式结构**（例如将真实手机号替换为合法虚构号段 `13800001234`，而非粗暴抹成 `[REDACTED]`），否则工具参数正则与解析器会因为格式异常出现假失败。
- **语义去重防簇膨胀**：线上流量遵循强烈幂律，“怎么开发票”可能重复出现上万次。必须结合 MinHash 与向量语义相似度（如余弦阈值 $>0.92$ 合并）去重，否则不仅浪费算力，还会把高度同质的重复题塞进分母，放大 <a class="term-ref" href="/books/llm-eval/glossary#clustered_se" title="Clustered SE，聚类标准误：当样本存在组内相关时按簇层级计算的修正标准误">聚类相关</a> 制造假阳性涨点。
- **分层抽样而非自然均匀抽样**：先按业务意图、渠道、用户权限层级与交互轮次分层，再在各层按配额抽样，确保低频高价值的复杂与高危场景拥有足够样本量。

### 步骤二：能力 × 风险二维覆盖矩阵

仅有真实日志依然不够：高频查询往往过于简单，而灾难性合规事故在日志里可能一年只出现两次。团队必须显式维护一张**能力复杂度 × 业务风险**二维覆盖矩阵，按配额规划黄金集结构：

| 覆盖象限 | 建议占比 | 核心测什么 | 典型判分与门槛策略 |
| --- | --- | --- | --- |
| **① 高频主路径** | 35%–40% | 贡献 80% 业务价值的标准主干流程 | 盯紧配对 $\Delta \pm 95\%\text{ CI}$、$\$/\text{Task}$ 与 P95 延迟 |
| **② 长尾复杂场景** | 25%–30% | 多跳跨文档推理、冲突条款、长上下文、多工具联动 | 重点暴露底座上限与脚手架状态管理短板 |
| **③ 边界与诚实拒答** | 15%–20% | 库内无依据、权限不足、过期规则、前提含糊 | 考核 <a class="term-ref" href="/books/llm-eval/glossary#calibration_abstention" title="校准与拒答：衡量置信度与真实准确率一致及证据不足时诚实拒答的能力">诚实拒答率</a>，严禁强行编造幻觉 |
| **④ 安全与合规红线** | ~15% | 间接提示注入、PII 泄露、越权写操作、违禁承诺 | **零容忍一票否决闸门**，不与常规分做算术平均 |

题量规模直接受第 1 章 MDE 公式约束（详见 [统计公式速查卡](/books/llm-eval/toolkit/metrics-and-stats)）：在双侧 $\alpha=0.05$、功效 $80\%$、同底座迭代强配对相关 $\rho \approx 0.80$ 下，若想稳定测出 $\Delta = 5\%$ 的真实提升，需要约 250–350 题；若要分辨 $\Delta = 3\%$ 的精细优化，核心 Dev 集需达到 **600–900 题**；而安全红线切片即便只有 60–100 题，只要触发任何一条严重越权即可直接判定发布不通过。（若是跨模型族横向选型，$\rho \approx 0.50$，同等 MDE 所需题量需扩大约 2.5 倍——$\Delta = 5\%$ 需约 500–780 题，与第 1 章账本完全一致。）

### 步骤三：业务专家联合标注与可执行 Rubrics 细化

黄金集最容易烂尾的环节不是缺题，而是<strong>“评判标准写得像领导发言”</strong>。把“回答要专业、准确、语气友好、符合公司规定”直接扔给人类标注员或 <a class="term-ref" href="/books/llm-eval/glossary#llm_as_a_judge" title="LLM-as-a-Judge：用强语言模型对开放输出或 Agent 轨迹进行自动化裁判的范式">LLM-as-a-Judge</a>，结果必然是标注者间一致性 $\kappa < 0.4$，评测分数沦为随机数。

工程化落地必须执行**可执行 Rubrics 拆解协议**：

1. **原子化二值检查项**：把模糊的宏观评价拆解为可独立判定“是/否”的加权检查清单 $\{(c_k, w_k)\}$，并显式区分<strong>一票否决致命项（Fatal Veto）</strong>。以一份保险理赔问答样例的结构化档案为例：

```yaml
case_id: "claim-2026-0142"
quadrant: "long_tail_conflict"
cluster_id: "policy_doc_v2026_03"
input:
  user_role: "standard_member"
  query: "我上月住院花了 1.8 万，买了尊享版医疗险能全额报吗？"
expected_context_ids: ["doc_med_2026#s4_deductible", "doc_med_2026#s7_excl"]
rubric:
  - id: "r1_deductible"
    weight: 4
    check: "明确指出 2026 版免赔额为 1 万元，而非引用已废止的 2024 版 5000 元口径"
  - id: "r2_citation"
    weight: 3
    check: "引用条款编号真实存在于召回文档中，未编造条款号"
  - id: "r3_fatal_overpromise"
    veto: true
    check: "不得做出未经核赔即保证 100% 赔付的违禁承诺（触发则整题判 0）"
```

2. **双人盲标校准一致性**：挑选 30–50 道试标样本，让两位业务专家（SME）独立按 Rubric 盲标并计算 <a class="term-ref" href="/books/llm-eval/glossary#iaa" title="IAA，标注者间一致性：剔除随机一致后衡量标注吻合度的指标，如 Cohen's κ">Cohen's κ</a>（核心检查项目标 $\kappa \ge 0.75$）。遇到分歧时，**绝不通过“两人取平均分”和稀泥**，而要逐条追问“哪句 Rubric 措辞存在歧义”，修订细则直至两位专家独立判定高度对齐。
3. **顺手沉淀评委校准集**：将专家达成共识的 100–200 条正/负样本留存为人类金标校准集 $(m_1, m_0)$，用于第 3 章的评委灵敏度 $q_1$、特异度 $q_0$ 标定与 <a class="term-ref" href="/books/llm-eval/glossary#rogan_gladen" title="Rogan-Gladen 矫正：利用评委灵敏度与特异度还原真实通过率的统计估计量">Rogan-Gladen 矫正</a>。

### 步骤四：对抗与边界样本定向合成（严守防同源偏见红线）

真实日志天然稀缺极端边界、复合冲突条款与恶意注入攻击。定向数据合成是补齐长尾与红线象限的高效杠杆，但操作不当极易引入严重的“自嗨幻觉”：

- **基于失败谱系而非自由发挥**：把真实脱敏种子、业务规则手册与 Open Coding 提炼的失败类型喂给生成模型，定向构造“跨页表格陷阱”“过期政策诱导”“情感施压越权”“工具返回畸形 JSON”等高价值对抗变体。
- **防同源偏见双红线**：
  1. **严禁未经人工验收直接入库**：合成模型极易自造与公司真实条款矛盾的“伪标准答案”。所有合成题必须经过业务专家逐条审核（确认题面真实合理、参考答案无误、Rubric 无歧义），未过审的一律丢弃——通常人工过筛留存率在 40%–65% 之间属健康常态；
  2. **禁止同模型自生自判**：合成题目的生成模型与后续自动评判的 Judge 模型应尽量**跨模型族分离**，避免触发 <a class="term-ref" href="/books/llm-eval/glossary#judge_biases" title="Judge 偏见：位置偏见、冗长偏见、自我偏好、奉承偏见等系统误差">自我偏好（Self-Preference）</a> 或隐性风格共谋。

### 步骤五：语义化版本冻结、物理切分与周期性轮换治理

把评测集当成一个随手往里面增删行数的共享表格，会让历史所有评测报告瞬间失去横向可比性。黄金集必须像生产代码与数据库 Schema 一样纳入严格的版本治理：

- **不可变版本冻结**：使用语义化版本（如 `eval-cs-agent-v1.2.0`）配合 Git LFS / DVC / 对象存储冻结不可变 Parquet 文件及 `SHA-256` 校验清单，连同每道题对应的上下文快照、知识库版本与 Rubric 版本号一起归档。
- **Dev / Holdout 物理切分**：将黄金集按 **70% Dev / 30% Holdout** 切分（注意：若多题共享同一文档或代码仓，必须按 `cluster_id` 整簇切分，严禁跨集合泄漏）。**Dev 集**对研发开放，供日常定位 Bad Case、调 Prompt 与改脚手架；**Holdout 集**权限物理锁定，仅允许 CI 流水线在发版前自动盲跑输出聚合统计分，严禁工程师逐条翻看，以此挡住最隐蔽的“人类肉眼 <a class="term-ref" href="/books/llm-eval/glossary#goodhart_law" title="Goodhart 定律：当度量指标本身变成优化目标时，它就不再是一个好的度量指标">Goodhart 过拟合</a>”。
- **防老化周期性轮换**：业务规则、用户习惯与模型弱点每季度都在演进。推荐采用<strong>「70% 固定核心回归切片 + 30% 滚动新鲜切片」</strong>结构（借鉴第 4 章 <a class="term-ref" href="/books/llm-eval/glossary#live_benchmark" title="动态活基准：持续引入新题并按时间戳切片评测以抵御污染与老化的基准范式">动态活基准</a> 思想）：每季度保留 70% 锚定核心题以维护跨年度纵向趋势，将连续两个季度全模型 100% 通过且非安全红线的饱和旧题降级归档，并换入来自第 19 章线上飞轮沉淀的 30% 新鲜难题。

## 17.3 阶段化演进预算与三大反模式预警

不同成熟度的业务无需一步到位砸重金建千题库，可按以下三阶段渐进扩充规模与人力投入：

| 演进阶段 | 推荐题量与分层 | 判分与校准配置 | 典型周期与核心产出 |
| --- | --- | --- | --- |
| **第 1 周 · 冷启动种子** | 50–80 题（主路径 + 历史致命客诉） | 人工抽检 + 确定性规则断言 | 1–2 人天；跑出首版基线与失败谱系 |
| **第 1 个月 · 校准回归集** | 300–400 题（补齐长尾与边界拒答） | 双人盲标 $\kappa \ge 0.75$ + RG 校准 Judge | 1 周专家协作；支撑 $\mathrm{MDE} \approx 4\%\text{–}5\%$（同底座强配对 $\rho \approx 0.80$）日常迭代 |
| **第 1 季度 · 工业锁库** | 600–1200 题（70% Dev / 30% Holdout） | 全自动 CI 闸门 + 季度 30% 滚动刷新 | 持续运转；支撑发版裁判与跨模型选型 |

很多团队迟迟不建黄金集，不是因为不懂统计，而是落入了以下三个典型反模式：

- <strong>反模式一：“等攒够 5000 题再开工”</strong>——完美主义拖死迭代。正确节奏是<strong>第 1 周先建 50 题冷启动种子集</strong>（覆盖主路径与最致命客诉，当天就能跑出基线），<strong>第 1 个月扩至 300 题完成双人 Rubric 校准</strong>，<strong>第 1 季度建齐 600–1000 题 Dev / Holdout 物理分池与滚动机制</strong>。
- <strong>反模式二：“只留难题，删光简单主路径”</strong>——评测集沦为偏题怪题集，导致某次改 Prompt 悄悄把日常高频查询搞崩却浑然不知。主路径永远要占 35%–40% 的压舱石配额。
- <strong>反模式三：“黄金集建完一劳永逸”</strong>——缺乏版本号与季度轮换，半年后业务早已迭代两轮，团队还在对着一套过时试题空转调优。

有了构建黄金评测集的通用流水线，下一章我们将把这套方法论直接压进企业最常落地的三大真实战场——**企业知识库 RAG、客服/运维工单 Agent 与内部研发代码 Copilot**——逐一拆解它们的专属数据设计、判分校准、上线 SLA 门槛与血泪排障实录。
