# 第 4 章 人类校准协议与数据污染防治

<p class="chapter-summary">落地用 100–300 题小样本人类金标校准自动化评委的完整工程协议，深度对比 Cohen's κ、Fleiss' κ 与 Krippendorff's α_K 及高不平衡下的 κ 悖论，并构建覆盖三类数据污染检测、动态活基准与企业三层留存轮换的纵深防线。</p>

第 3 章的 Rogan-Gladen 公式指明了一个残酷的现实：如果人类校准集本身标注混乱、充满分歧，或者整套评测题目早在预训练阶段就已经泄漏进了模型权重里，那么再漂亮的统计公式也只是在给虚假分数“精装修”。本章补齐第一篇最后两块基石：前半部分解决**如何用 100–300 题的高纯度人类金标把裁判锚定在真实业务标准上**；后半部分解决**如何在数据污染泛滥的时代保卫评测集的新鲜度与区分力**。

---

## 4.1 小样本人类金标校准协议（100–300 题实战闭环）

企业团队常陷入两个极端：要么嫌人工标注太贵干脆裸奔上 LLM Judge，要么大动干戈招几十名外包标几万条却毫无质控。结合第 3 章 Delta 方差账本，**100–300 题（正负例各 50–150 题）的高质量专家金标**正是信噪比与成本的黄金甜点。标准落地协议包含五个严格串联的阶段：

1. <strong>分层抽样（Stratified Sampling）</strong>：切忌纯随机抽取——如果线上基线通过率高达 95%，随机抽 100 题只能抓到 5 条负例，根本无法准确估计评委特异度 $q_0$（负例方差直接爆炸）。应结合模型版本、任务难度与初筛置信度做分层过采样，刻意让校准集的正负例比例落在 <strong>30%–70%</strong> 区间，同时覆盖基线与主要候选模型家族，防范 $(q_1, q_0)$ 漂移。
2. **操作化标注指南与 20–30 题试标对齐**：绝不能给标注员丢一句“请按有用性打 1–5 分”。指南必须给出每档边界的**操作化定义**、至少 3 对容易吵架的边界正反例，以及明确的“不可判定/系统异常”弃权规则。先由核心业务专家独立试标 20–30 题，开对齐会逐题复盘分歧、迭代指南直至一致性达标，再进入正式标注。
3. **双盲 / 三盲独立标注与仲裁**：向标注界面彻底隐藏模型名称、生成耗时与自动评委初判（防锚定）；Pairwise 界面随机打乱左右次序。每道题至少由 **2 名独立标注员**背靠背打标；分歧样本交由第 3 名资深仲裁专家（Adjudicator）盲审拍板，避免“多数外包压倒领域专家”的劣币驱逐良币。
4. <strong>黄金蜜罐题质检（Golden Honeypots）</strong>：在正式标注队列中无征兆混入 <strong>5%–10%</strong> 由资深专家预先锁死答案的陷阱题（含隐蔽幻觉、格式细微违规等）。任何标注员在蜜罐题上准确率低于 85% 或单题停留时间异常过短，其整批标注直接回炉重标。
5. **冻结金标与独立留存验证**：锁定 100–300 题金标后，在完全相同数据上运行候选 LLM Judge 计算 $(q_1, q_0, J, \kappa)$，并将分歧最集中的误判案例提炼为 Judge Prompt 的反例锚点。切记：用于优化 Judge 的“开发调试集”必须与估算 $(q_1, q_0)$ 的“留存校准集”严格切分，防止评委过拟合校准集导致 $q_1, q_0$ 虚高。

| 校准集规模 ($m_1 + m_0$) | $q_0 = 0.80$ 时的估计标准误 | 双人盲标估算人时（单题 2 分钟） | 适用工程阶段 |
| --- | --- | --- | --- |
| <strong>60 题（30 正 + 30 负）</strong> | $\pm 7.3\text{ pp}$ | 约 4 人时 | 早期原型的 Judge 快速冒烟与 Rubric 排错 |
| <strong>150 题（75 正 + 75 负）</strong> | $\pm 4.6\text{ pp}$ | 约 10 人时 | 绿灯评委（$J \ge 0.70$）的常规 RG 校准基准 |
| <strong>300 题（150 正 + 150 负）</strong> | $\pm 3.3\text{ pp}$ | 约 20 人时 | 核心上线闸门、跨家族选型或黄灯评委的精密校准 |

## 4.2 标注者间一致性（IAA）深度对比与 $\kappa$ 悖论

衡量两名人类专家之间，或“人类金标与 LLM Judge”之间有多一致，绝不能只报原始一致率 $p_o$——如果 90% 的回复本来就该判通过，两个闭眼全打“通过”的懒惰裁判也能轻松刷出 81% 的表面一致率。测量学要求使用剔除随机猜对概率的<a class="term-ref" href="/books/llm-eval/glossary#iaa" title="剔除随机一致概率后衡量多位专家或人机判分吻合度的统计指标">标注者间一致性（IAA）</a>指标：

$$
\text{Cohen's / Fleiss' }\kappa = \frac{p_o - p_e}{1 - p_e}, \qquad
\text{Krippendorff's }\alpha_K = 1 - \frac{D_o}{D_e}
$$

其中 $p_o$ 与 $p_e$ 分别为观测一致率与边际独立假设下的期望随机一致率；$D_o$ 与 $D_e$ 分别为基于量表距离函数 $\delta^2(c, c')$ 计算的观测分歧度与随机期望分歧度。三大核心指标的适用场景对比如下：

| 一致性指标 | 标注人数 | 缺失值容忍 | 支持量表类型 | 工程选型建议 |
| --- | --- | --- | --- | --- |
| **Cohen's $\kappa$**（含加权 $\kappa_w$） | 严格 2 人 | 不支持 | 标称 / 有序（线性或平方加权） | 最常用于“人类金标 vs 单个 LLM Judge”人机对齐评测 |
| **Fleiss' $\kappa$** | $M \ge 3$ 人 | 要求每题满员 | 仅标称分类（无序） | 适用于每题均由固定 $M$ 人完整标注的二值/多分类任务 |
| **Krippendorff's $\alpha_K$** | 任意人数 | **原生支持稀疏缺失** | **标称 / 有序 / 区间 / 比率全通吃** | **工业界多人标注黄金标准**（尤其适合众包与 1–5 分有序量表） |

一般工程门槛：$\alpha_K$ 或 $\kappa \ge 0.80$ 表明指南清晰、结论可靠；$0.67\text{–}0.80$ 仅可作探索性参考；低于 $0.60$ 时不要急着怪模型或换 Judge——**连人类专家自己都无法达成共识的任务，任何自动化裁判都注定失效**，必须回头重写任务定义与 Rubric。

### 高类别不平衡时的 $\kappa$ 悖论（Feinstein & Cicchetti 算例）

工程实践中经常遇到一个令人困惑的异常：明明两位资深安全专家达成 96% 的超高共识，算出来的 Cohen's $\kappa$ 却只有惨淡的 0.48！让我们用确切数字拆解这一著名的 **$\kappa$ 悖论**：

假设 100 条安全审查样本中，两位专家共同判“安全” 94 条、共同判“违规” 2 条，仅在 4 条边界样本上各执一词（$a = 94, b = 2, c = 2, d = 2$）。此时：
- 原始一致率 $p_o = (94 + 2) / 100 = 0.96$；
- 两位专家各自的边际“安全”率均为 $96\%$、“违规”率均为 $4\%$，于是期望随机一致率被极端不平衡的分布推高到 $p_e = 0.96^2 + 0.04^2 = 0.9232$；
- 代入公式得 $\kappa = (0.96 - 0.9232) / (1 - 0.9232) = 0.0368 / 0.0768 = \mathbf{0.479}$！

| 同一批 100 条双标结果上的诊断指标 | 实测数值 | 解读与工程信号 |
| --- | --- | --- |
| **原始一致率 $p_o$** | 96.0% | 容易虚高，掩盖稀有类上的真实分歧 |
| **Cohen's $\kappa$** | **0.479** | 受 96%/4% 极端偏态惩罚，表面看起来“接近不及格” |
| **稀有类（违规）互评 F1** | **0.500** | 一针见血：在真正关心的 6 条疑似违规样本里，两人只对上了 2 条！ |
| **Gwet's AC1** | 0.957 | 对边际偏态稳健，反映总体分类稳定性 |

**教训与解药**：当罕见事件（如线上严重安全违规、低频工具崩坏）占比低于 10% 或高于 90% 时，$p_e$ 逼近 1 会剧烈放大极少数分歧对 $\kappa$ 的惩罚。解决之道有二：其一，回到 4.1 节的**分层过采样**，在构建校准集时刻意富集负例至 30%–70%；其二，在无法改变极端偏态的线上抽检报告中，**同步汇报稀有类的类内 F1 与 Gwet's AC1**，绝不拿着单一裸 $\kappa$ 误判标注质量。

## 4.3 三类数据污染形态与检测探针的边界

即使评委与金标无懈可击，一旦测试题通过预训练语料或迭代反馈提前“泄题”，<a class="term-ref" href="/books/llm-eval/glossary#data_contamination" title="评测集的题目、答案或改写变体混入训练语料或经反馈过拟合导致离线分数虚高">数据污染（Data Contamination）</a>就会把“真泛化”悄悄偷换成“背原题”。工程上必须同时警惕隐蔽程度逐级递增的三类污染：

1. <strong>Ⅰ 类：原题直泄（Verbatim Leakage）</strong>：公开基准（如早期 GSM8K、MMLU、HumanEval）的题面、选项与标准答案直接随 GitHub 仓库或网页快照混入预训练或 SFT 数据集。
2. <strong>Ⅱ 类：改写与翻译语义泄漏（Paraphrase / Translation Leakage）</strong>：Yang 等人（2023）的实验证明，只要用强模型把测试集做同义改写、换语言翻译或合成同构变体混入微调语料，就能**100% 绕过主流的 13-gram 字面查重**，同时让小模型在目标榜单上凭空暴涨 20–30 个百分点。
3. <strong>Ⅲ 类：评测反馈间接过拟合（Adaptive Overfitting）</strong>：最隐蔽也最容易被团队自我合理化的污染——测试题从未进过一行训练代码，但算法团队连续数月紧盯同一份固定测试集筛选预训练数据配比、微调 RL 奖励权重与 Prompt 措辞，最终靠人工试错把测试集特征硬编码进了系统里。

### 多层污染检测手段及其局限

| 检测手段 | 原理与代表方法 | 适用前提 | 典型盲区与工程局限 |
| --- | --- | --- | --- |
| **语料级查重** | 13-gram 精确匹配、MinHash-LSH 局部敏感哈希 | 拥有训练语料访问权（模型自研方内部审计） | 对闭源 API 无能为力；完全漏检 Ⅱ 类改写与翻译泄漏 |
| **似然与成员推断** | **Min-K% Prob**（Shi 等, 2024）检验低概率词异常高似然；多选题选项乱序性能退化 | 需暴露 token logprob 接口（灰盒） | 经 SFT/RLHF 分布重塑后似然噪声极大，单凭阈值误报/漏报率均高 |
| **结构扰动行为探针** | **GSM-Symbolic**（Mirzadeh 等, 2024）、**GSM1k**：同构替换人名/数值或插入单句无关干扰（`NoOp`） | **纯黑盒可用**，无需权重与语料 | 需维护参数化题目模板；能暴露浅层模式记忆，但难区分“背题”与“泛化脆弱” |

Mirzadeh 等人在 **GSM-Symbolic** 中的发现尤其振聋发聩：给定一道经典小学应用题（“Oliver 周五摘了 44 个猕猴桃，周六摘了 58 个，周日摘了周五的两倍，三天共摘多少个？”），仅仅替换人名与数字，前沿模型便出现明显方差；而在题干末尾加入**一句与计算完全无关的干扰信息**（“但其中有 5 个猕猴桃比平均尺寸略小”，即 `GSM-NoOp`），模型却习惯性地从总数里减去 5，导致主流前沿模型准确率应声<strong>绝对暴跌 17.5–65.7 个百分点（pp）</strong>！这一实验用最朴素的黑盒行为探针戳穿了静态基准上的高分幻觉：模型往往只是在匹配训练语料里见过的表层句式模板，而非执行稳健的符号推理。

### 外部选型：动态活基准与时间截断切片

面向公开大模型选型时，应优先采信具备持续出题机制的<a class="term-ref" href="/books/llm-eval/glossary#live_benchmark" title="持续引入知识截断日期之后的新题并按时间戳切片评测以抵御数据污染的基准范式">动态活基准（Live Benchmark）</a>：
- **LiveCodeBench**（Jain 等, 2024）持续抓取 LeetCode、AtCoder、Codeforces 的最新竞赛题，每道题绑定精确发布时间戳。评测时按模型的知识截止日期切分“截止日前 vs 截止日后”两段子集——若某模型在旧题上 75% 而在截断日后的新题上断崖跌至 40%，污染铁证如山；
- **SWE-bench Live**、**LiveBench** 等新一代基准则通过月度滚动纳入近期真实 GitHub Issue 与带确定性验证的新编推理题，彻底终结“一张试卷考三年”的刷榜闹剧。

### 企业落地：三层私有留存集轮换架构

对于企业自建评测体系（第 17 章详述<a class="term-ref" href="/books/llm-eval/glossary#edd" title="Evaluation-Driven Development，将业务黄金评测集置于 Prompt、脚手架与模型开发之前的工程范式">评测驱动开发 EDD</a> 落地细则），必须从第一天起建立**三层隔离与定期轮换制度**：

| 层级 | 权限与可见范围 | 轮换与维护策略 | 允许用途与治理红线 |
| --- | --- | --- | --- |
| <strong>Tier 1 · 开发/CI 快测集</strong> | 对算法与产品研发完全透明 | 随线上 Badcase 持续追加 | 日常 Prompt 调试、误差归因与 PR 门禁；接受其逐步过拟合，不作终审 |
| <strong>Tier 2 · 密封留存闸门</strong> | 仅评测平台权限隔离只读 | 严禁暴露单题，仅返回聚合 CI | 版本发布候选（RC）与底座切换唯一终审；**严禁回流训练或 Few-shot** |
| <strong>Tier 3 · 季度轮换金丝雀</strong> | 评测团队按月/季动态抽样 | 每季替换 Tier 2 中 20%–30% 旧题 | 注入脱敏线上新单与扰动变体，附带 **Canary UUID** 禁入库指纹 |

特别提醒最后一项防内鬼措施：在所有内部评测集与黄金标注文件中嵌入类似 BIG-bench 的<strong>唯一金丝雀指纹字符串（Canary UUID）</strong>，并在公司内部数据湖清洗、SFT 构造与预训练抓取管线中配置硬拦截规则——一旦扫描到金丝雀指纹立即整批丢弃并触发告警，从基础设施层彻底堵死内部“左手倒右手”的意外污染。

::: warning 评测资产同样需要语义化版本号（SemVer）
