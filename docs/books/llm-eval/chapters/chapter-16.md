# 第 16 章 系统化误差分析、失败谱系与评审报告规范

<p class="chapter-summary">走出“只报总分 68.4%”的无效汇报陷阱：落地源自质性研究的 Open Coding 到 Axial Coding 抽样编码法，掌握工业界高频复现的 Agent 七大根因失败谱系，并确立经得起架构与上线审批的 Evaluation Card 七大强制规范。</p>

几乎每个做过 LLM 应用的团队都见过这样的周报：“本周升级了 Prompt 与工具描述，在内部 500 题测试集上通过率从 66.8% 提升到 68.4%。”看似进展喜人，但在研发评审会上只要追问两个问题就会瞬间冷场——第一，1.6 个百分点在 500 题上过了显著性检验吗？第二，剩下的 <strong>31.6%（158 条失败样本）到底死在哪里，下周该改哪一行代码？</strong>

评测的终极目的不是产出给排行榜看的装饰数字，而是为下一次工程迭代提供高信噪比的**根因诊断**。本章系统化拆解从失败轨迹中提炼行动指令的编码方法、工业界 Agent 七大根因谱系，以及面向架构与上线决策的标准评审报告范式。

## 16.1 从“看总分”到 Open Coding → Axial Coding 抽样编码法

当面对上百条动辄数万 Token 的多轮失败轨迹时，工程师最容易陷入两个极端：要么走马观花挑两三条“看着离谱的”案例拍脑袋改 Prompt（严重受幸存者与可得性偏差误导），要么偷懒直接把全部日志丢给另一个大模型自动总结（往往产出“逻辑不清 55%、理解偏差 30%”这类空洞套话）。

工业界验证最有效的落地方法，是借鉴质性研究扎根理论（Grounded Theory）的<strong><a class="term-ref" href="/books/llm-eval/glossary#open_coding" title="不预设先验标签，人工通读 50–100 条真实失败轨迹并自下而上收敛为互斥根因谱系的系统化误差分析方法">Open Coding（开放编码）</a> → Axial Coding（主轴归类）</strong>四步闭环：

<figure class="book-figure">
  <img src="/figures/llm-eval/agent-failure-taxonomy.svg" alt="Open Coding 抽样收敛流程与 Agent 七大根因失败谱系帕累托归因图" loading="lazy">
  <figcaption><span class="book-figure__label">图 16-1</span>自下而上的四步误差编码闭环（上）与某多轮 Agent 100 条失败轨迹的七大根因帕累托归因示例（下）。前三类根因往往吞掉 60%–75% 的失败，是最高杠杆的修复靶点。</figcaption>
</figure>

1. <strong>去噪随机分层抽样（50–100 条）</strong>：先彻底剥离[第 14 章](/books/llm-eval/chapters/chapter-14)定义的 <a class="term-ref" href="/books/llm-eval/glossary#infra_vs_model_error" title="基础设施异常与模型能力失败严格分桶统计">infra_error</a> 桶，再从纯 `model_failure` 样本中按业务场景或难度**随机分层抽取 50–100 条轨迹**（若总失败不足 50 条则全量通读）。严禁只挑“得分最低”或“最显眼”的案例；
2. <strong>Open Coding（开放编码，锁定首个致命拐点）</strong>：不预设分类表，由核心研发与领域专家亲自逐条通读轨迹，写下一句具体现象笔记。**黄金铁律是只记“首个不可逆致命拐点（First Fatal Mistake）”而非下游连锁症状**——例如第 2 轮把时间过滤字段写成 `YYYY/MM/DD` 而非 ISO 格式导致查出空列表，模型在第 5 轮只好编造答案，根因在第 2 轮工具参数错，而不是第 5 轮幻觉；
3. <strong>Axial Coding（主轴归类，收敛 MECE 谱系）</strong>：读完前 40–50 条笔记后，将语义高度重叠的自由现象合并聚类，提炼出 5–8 个<strong>互斥、无遗漏（MECE）</strong>的根因类目，并为每一类写清判定边界与反例；
4. **理论饱和检验与标注一致性对齐**：继续编码下一批 20–30 条新样本；若连续 20 条样本都能干净落入已有类目且不再催生新类别，即达到<strong>理论饱和（Theoretical Saturation）</strong>。多人协作编码时，抽取 20 条双盲交叉标注并检验 <a class="term-ref" href="/books/llm-eval/glossary#iaa" title="标注者间一致性，剔除随机一致后的吻合度系数如 Cohen's Kappa">Cohen's Kappa</a>（要求 $\kappa \ge 0.75$），确保口径统一。

下表展示一份可直接复用的 **Open Coding → Axial Coding 轨迹编码表** 片段，体现如何把杂乱日志转化为精准排障指令：

| 轨迹 ID | 首个致命拐点 | Open Coding 自由现象笔记 | Axial Coding 归类 | 指向修复动作 |
| --- | --- | --- | --- | --- |
| `tr-0142` | 第 2 轮 | 调用 `query_orders` 时传入 `date="2026/10/01"`，工具要求 ISO-8601 致返回空集，后续开始瞎猜 | ① 工具参数构造错 | 在 Schema 中写明正则格式并加字段校验报错 |
| `tr-0289` | 第 4 轮 | 工具明确返回 `HTTP 403: 需主管审批`，模型忽略报错直接回复用户“已为您提交退款” | ③ 观测误读 / ⑥ 虚报 | 高亮错误码并要求终答引用真实回执单号 |
| `tr-0317` | 第 11 轮 | 前序读了 6 份长工单后遗忘系统提示词里“超过 7 天不可免邮退货”的硬规则 | ④ 长上下文政策漏遵 | 折叠历史工单正文，将退款硬规则置入最近轮次 |
| `tr-0405` | 第 6–12 轮 | 用完全相同的 `user_id` 连续重试 `fetch_profile` 6 次均返回 404，直至触达最大步数 | ⑤ 死循环与无进展重试 | Runtime 检测连续 2 次同参失败即强制提示换路径 |

::: tip 何时引入 LLM 辅助批量分类？
**先人后机，切忌本末倒置**。只有当人类团队完成 50–100 条 Open Coding 并锁定精确的 Axial Coding 定义、边界条件与正反例之后，才可以将这套类目表写成 Prompt，交给强模型对剩余数千条历史或线上轨迹做批量归因统计（并按第 3 章方法做抽检校准）。未经人工深读轨迹就全自动聚类，永远发现不了隐藏在 Schema 细节和业务暗规则里的真问题。
:::

## 16.2 工业界高频复现：Agent 七大根因失败谱系

尽管各行业业务千差万别，跨 SWE、工单客服、深度检索与数据运维等生产 Agent 复盘后，失败根因高度收敛为以下七大经典谱系（示例占比对应图 16-1 的 100 条失败轨迹算例）：

| 编号与根因谱系 | 示例占比 | 典型轨迹征兆 | 归属责任层 | 首要工程修复抓手 |
| --- | --- | --- | --- | --- |
| **① 工具选择与参数构造错** | 27% | 选错近似工具、参数类型/日期格式错、必填枚举值凭空杜撰、嵌套 JSON 语法非法 | 脚手架 / Schema | 合并冗余工具、精简并举例重写 Tool Schema；在执行器层增加参数校验与友好修正提示 |
| **② 规划跑偏 / 目标拆解错** | 21% | 漏掉用户复合约束、执行顺序颠倒（先删后查）、上来就调用不相关工具 | 模型推理 / 路由 | 前置显式计划步骤；复杂多约束题按[第 15 章](/books/llm-eval/chapters/chapter-15)路由至强推理底座 |
| **③ 环境观测误读 / 无视报错** | 16% | 工具已明确返回 `403` 或空结果，模型却熟视无睹继续往下推演，或错读表格行列 | 脚手架 / 模型 | 结构化提取并高亮工具报错摘要；在脚手架注入“先复述报错原因再决断下一步”约束 |
| **④ 长上下文遗忘 / 政策漏遵** | 13% | 多轮交互超过 10 轮后遗忘系统提示词里的退款红线、越权审批或漏用早期查到的 ID | 脚手架 / 长文能力 | 动态上下文折叠（清理冗长 HTML/日志）；将高危业务红线与关键实体置于最近一轮上下文尾部 |
| **⑤ 死循环与无进展重试** | 10% | 用几乎完全相同的参数反复调用同一报错工具直至撞碎最大步数上限 | 脚手架运行时 | 在 Runtime 层检测连续重复调用指纹，自动阻断并向模型注入“禁止重复同参，请换路径或求助” |
| **⑥ 过早放弃或虚报成功** | 8% | 遇轻微阻力直接敷衍“无法完成”，或在未真正修改数据库/文件时就宣称“已修复完毕” | 模型对齐 / 提示 | 强制终答必须引用工具返回的真实对象 ID 或退出码；针对虚报行为构建负样本做针对性后训练 |
| **⑦ 缺乏终态自检与验证** | 5% | 写完代码或改完配置直接交卷，未跑单测/Lint 或未复查终态导致低级语法与边界缺陷 | 脚手架钩子 | 在<a class="term-ref" href="/books/llm-eval/glossary#scaffold" title="包裹在底层 LLM 之外的系统提示词、工具封装、循环规划与重试编排逻辑">脚手架</a>提交动作前挂载强制只读<a class="term-ref" href="/books/llm-eval/glossary#final_state_assertion" title="通过检查环境最终状态而非中间文本的客观验证方法">终态自检</a>钩子（自动跑测试/校验和并回传结果） |

看懂这张表就能立刻洞察一个极具颠覆性的工程真相：在图 16-1 的真实分布里，**工具参数错（27%）、观测误读（16%）、上下文遗忘（13%）、死循环（10%）与缺乏自检（5%）合计占去 71% 的失败，它们绝大多数可以通过改造脚手架与工具接口在数天内修复**，根本无需花费数月去重新微调或换昂贵的底座模型（这套“改脚手架 vs 改模型”的系统决策矩阵将在[第 20 章](/books/llm-eval/chapters/chapter-20)彻底展开）。

### 编码标注中三组高频易混边界的判定口径

多人团队做 Open Coding 时，最常导致标注一致性 $\kappa < 0.75$ 的分歧集中在三组边界，建议写进团队标注手册：

- **① 工具描述歧义 vs ② 规划跑偏**：先让人类专家在**只看模型所见系统提示词与 Tool Schema**的前提下做一遍。如果连人类专家都分不清 `search_order` 和 `query_order` 的入参差别，必须判给 **① 工具 Schema 缺陷**，而不是怪模型规划能力差；
- **③ 观测误读 vs ④ 长上下文遗忘**：关键信息出现在**紧邻上一轮**工具返回中却被模型无视，归为 **③ 观测误读**；关键政策或实体出现在 8 轮之前、被数万 Token 历史日志淹没后才丢失，才归为 **④ 长上下文遗忘**；
- **⑤ 死循环 vs `infra_error`**：若外部工具稳定返回确定性的业务错误（如 `400 Invalid Date`）而模型反复传同一坏参直至超步数，归为 **⑤ 模型死循环**；若外部接口随机抛出 502/超时致无法推进，应退回[第 14 章](/books/llm-eval/chapters/chapter-14)的 `infra_error` 桶。

实践迭代时，建议每轮只集中攻坚 **Top-1 或 Top-2 根因** 后立刻重跑回归，避免一次改动十处导致正负效应相互抵消、无法归因。

## 16.3 评审级标准评测报告（Evaluation Card）七大强制区块

为了让评测真正发挥架构把关与上线审批作用，团队必须废除随意的截图和口头报数，将每次重要迭代沉淀为结构统一的 <strong>Evaluation Card（评审级评测卡）</strong>，强制包含以下七个区块：

| 强制区块 | 必须披露的核心要素 | 常见缺漏与审计红线 |
| --- | --- | --- |
| **1. 版本与环境指纹** | 模型权重/快照日期、脚手架 Git SHA、Prompt/Template 哈希、推理引擎与量化档位、沙箱镜像 Digest 与 VCR 磁带版本 | 只写“最新版模型”且无模板与代码 Commit，半年后无法复现 |
| **2. 样本量与统计显著性** | 有效样本量 $N_{\text{eff}}$、与基线的配对差值 $\Delta$、95% <a class="term-ref" href="/books/llm-eval/glossary#paired_bootstrap" title="成对重采样估计模型分差置信区间的非参数检验方法">Paired Bootstrap</a> / <a class="term-ref" href="/books/llm-eval/glossary#clustered_se" title="存在组内相关时按簇层级计算的修正标准误">Clustered SE</a> 置信区间、McNemar $p$ 值与当前 <a class="term-ref" href="/books/llm-eval/glossary#mde" title="给定题量与功效下可稳定检出的最小真实分差">MDE</a>（口径对齐[统计速查卡](/books/llm-eval/toolkit/metrics-and-stats)） | 只报标量总分不给 CI；把共享文档的子题当独立样本导致假阳性涨点 |
| **3. 分层能力切片** | 按业务域、任务难度、上下文长度、多轮步数、新旧样本拆解的子集得分对照表 | 用总体均值掩盖高价值核心场景暴跌 10 pp 的辛普森悖论 |
| **4. 基础设施健康审计** | `infra_error_rate`、自动重试次数、`finish_reason == "length"` 思考截断占比与沙箱超时率 | 隐瞒故障率，或把超过 2% 的基础设施报错混进分母/静默丢弃 |
| **5. 联合帕累托与成本延迟** | 单任务综合成本（`USD/Task`，含思考/重跑/缓存命中率）、TTFT 与 E2E P50/P95 延迟（注明测试并发 QPS）及 <a class="term-ref" href="/books/llm-eval/glossary#pareto_frontier" title="质量、成本与延迟多维最优折中前沿">帕累托前沿</a> 位置 | 报离线单并发平均耗时充当线上延迟，或遗漏隐式思考 Token 账单 |
| **6. Top-3 根因剖析与轨迹** | 50–100 条 Open Coding 根因帕累托分布、Top-3 根因各附 1–2 条脱敏典型轨迹链接及对应下阶段修复责任人 | 只有冷冰冰的数字表，没有任何人工审阅轨迹与可执行排障项 |
| **7. 上线结论与灰度边界** | 明确三选一结论（`Ship 全量` / `Canary 灰度` / `Block 阻断`）、已知盲区声明、线上回滚触发阈值与下一轮回归目标 | 模棱两可写“整体表现尚可，建议推进”，逃避明确工程担责 |

以下是一份可直接纳入团队评审模板的 **Evaluation Card 精简摘要实例**：

```yaml
evaluation_card:
  1_manifest: { candidate: "M3-cascade-v2.4", baseline: "M2-32b-fp8", git_sha: "c81e728", cassette_sha: "4e074085" }
  2_stats: { n_eff: 497, pass_rate: 0.805, delta_vs_base: "+9.5 pp", ci_95: "[+6.4, +12.6] pp", mcnemar_p: "< 1e-7", mde: "4.4 pp" }
  3_slices: { simple_ticket: 0.882, multi_hop_refund: 0.714, long_ctx_gt_32k: 0.690 }
  4_infra_audit: { infra_error_rate: 0.006, length_truncation_rate: 0.008, gate: "VALID (<= 2%)" }
  5_pareto_sla: { cost_usd_per_task: 0.062, cache_hit_rate: 0.81, e2e_p95_s_at_40qps: 18.4, sla_30s: "PASS" }
  6_top3_errors:
    - { cause: "Tool Schema 参数格式错", share: "27%", sample: "trace://tr-0142", owner: "@tools-team" }
    - { cause: "复合约束规划漏项", share: "21%", sample: "trace://tr-0208", owner: "@router-team" }
    - { cause: "忽略 403 报错继续执行", share: "16%", sample: "trace://tr-0289", owner: "@agent-core" }
  7_decision: { verdict: "CANARY_10PCT", rollback_if: "online_refund_violation > 0.2% or p95 > 25s" }
```

### 面向高效决策的 15 分钟评审会固定议程

拿到 Evaluation Card 后，评审会应严格按**先验真、再看分、后派活**的顺序推进，避免把时间浪费在无休止的个案争辩上：

1. <strong>前 2 分钟（一票否决核验）</strong>：直奔第 4 与第 1 区块，确认 `infra_error_rate ≤ 2%`、无长度截断异常、环境指纹完整；若用了 <a class="term-ref" href="/books/llm-eval/glossary#llm_as_a_judge" title="使用强语言模型对开放式生成或复杂 Agent 轨迹进行自动化判分的裁判范式">LLM-as-a-Judge</a> 判分，同时检查其是否按[第 3 章](/books/llm-eval/chapters/chapter-03)完成了 <a class="term-ref" href="/books/llm-eval/glossary#rogan_gladen" title="利用人类金标灵敏度与特异度对有偏观测通过率进行无偏还原的公式">Rogan-Gladen</a> 矫正；任一项不达标直接散会重测；
2. <strong>第 3–6 分钟（显著性与商业可行性）</strong>：对照第 2、3、5 区块，确认配对 95% CI 不跨零、无高价值核心切片回退，且并发 P95 与单任务成本落在帕累托绿灯区；
3. <strong>第 7–12 分钟（现场共读 Top-3 轨迹）</strong>：点开第 6 区块附带的 3 条典型失败轨迹原文，当场确认归因口径与修复归属（脚手架组 vs 路由组 vs 模型组），写入下周迭代 Issue；
4. <strong>最后 3 分钟（明确签字放行）</strong>：在第 7 区块锁定 `Ship` / `Canary` / `Block` 结论与自动回滚红线，将卡片归档为组织长期评测知识库。

### 从单次归因到跨周期根因趋势追踪

评审卡片不应在会议结束后尘封在 Wiki 角落，而应按迭代版本号（如 `v2.1 → v2.4`）持续沉淀七大根因的占比堆叠折线图。当团队连续两个迭代观察到以下信号时，即可触发架构层面的战略调整：

- **某一脚手架类根因（如工具参数错或死循环）骤降至 5% 以下**：说明前期 Schema 治理与 Runtime 护栏已见效，应立刻把研发带宽转向下一顺位瓶颈；
- **规划跑偏与复杂约束遗漏占比反升至 40% 以上**：说明外围脚手架的红利已逼近天花板，此时继续堆砌系统提示词往往得不偿失，必须转入升级推理底座、优化级联路由，或将脱敏失败轨迹安全导入[第 20 章](/books/llm-eval/chapters/chapter-20)的 SFT / RLVR 后训练闭环。

::: warning 架构评审会的一票否决红线
凡满足以下任意一条的评测报告，评审会应直接退回重做、严禁放行上线：① 未提供配对差值 95% 置信区间或样本量不足以覆盖宣称涨点；② `infra_error_rate > 2%` 或完全未披露异常桶；③ 缺失单任务成本与并发 P95 延迟的 SLA 校验；④ 拿不出基于至少 50 条失败轨迹的根因归类结论。
:::
