# 第 9 章 工具调用、MCP 编排与多轮用户交互评测

<p class="chapter-summary">工具调用是绝大多数企业 Agent 落地的第一主战场。本章沿着「静态 AST 校验 → 动态 MCP 工具发现与大工具集路由 → τ-bench / τ²-bench 双控政策与数据库终态哈希 → 用户模拟器防泄题治理」四级阶梯，建立直通生产稳定性的多轮工具交互评测体系。</p>

过去一年，几乎每家大模型厂商都在发布会上宣称自己的 Function Calling 准确率突破 90%。但企业把模型真正接入 CRM、ERP 或客服工单系统后，往往一周内就会遭遇惨烈现实：面对上百个业务接口时选错重载函数；用户根本没给订单号就胡编一个假 ID 去查库；后端偶发一个 `429` 限流或字段格式微调，整个对话直接卡死；甚至绕过审批红线私自给用户办了超额退款。

根源在于，绝大多数早期榜单测的只是“单轮照模板填 JSON 的能力”，而真实生产业务需要的是<strong>动态工具生态里的有状态多轮协同、业务政策遵从与连续高稳定性执行</strong>。本章按复杂度逐级拆解这一战场的四大核心板块。

---

## 9.1 从静态 AST 到多轮状态：BFCL 演进谱系

<strong>BFCL（Berkeley Function Calling Leaderboard）</strong>从 v1/v2 的单轮静态 AST 校验与真实用户 Live 集，一路演进至 v3 的有状态多轮交互，并在最新的 <strong>BFCL v4</strong> 中进一步扩展至网页检索、长期记忆与格式敏感性等 Agentic 评测维度（与 [评测避坑清单](/books/llm-eval/toolkit/eval-checklist) 中的 BFCL v3/v4 选型口径保持一致）。其核心演进子集的四级阶梯如下：

| 演进子集 | 核心测试能力 | 判定方式 | 工程价值与残余盲区 |
| --- | --- | --- | --- |
| <strong>Simple / Multiple / Parallel（v1）</strong> | 单工具填参、多候选消歧、单轮并发输出多个独立调用、复杂嵌套对象参数 | <strong><a class="term-ref" href="/books/llm-eval/glossary#deterministic_verifier" title="确定性验证器：通过 AST/Schema、单元测试或终态哈希给出客观判分的程序化裁判">AST 语法树与类型精确匹配</a></strong>（允许合法默认值等价） | 极快、零沙箱依赖，适合作为选型初筛；但无法检验真实执行后的语义等价与动态纠错 |
| **Irrelevance / Abstention** | 候选工具均无法满足需求，或缺少必填参数时主动<strong><a class="term-ref" href="/books/llm-eval/glossary#calibration_abstention" title="置信度校准与拒答：衡量模型确定性与真实正确率对齐程度及信息不足时的诚实拒答能力">缺参拒调</a></strong> | 检查模型是否输出空工具调用并转向自然语言澄清追问 | 拦截“盲目乱调接口”与“脑补假参数”顽疾，是生产客服与金融助手的关键前置门槛 |
| <strong>Live（v2 · 真实用户贡献集）</strong> | 社区真实复杂 Schema、不规范字段命名、冗长枚举值与脏文档 | AST 匹配 + 真实 API 文档语义约束校验 | 有效暴露“洁净学术 JSON 拿高分、一遇企业脏 Swagger 文档就崩溃”的分布外落差 |
| <strong>Multi-Turn / Multi-Step（v3）</strong> | 在文件系统、出行预订、交易账户中执行多步嵌套链式依赖、跨轮读写并追踪隐状态变化 | 执行真实本地状态机，比对<strong>终态状态字典</strong>与关键写操作序列 | 逼近真实 Agent 轨迹（v4 进一步叠加网页检索、记忆与格式敏感性测试），但仍以脚本化指令驱动，缺乏真实人类的模糊意图与政策博弈 |

在企业选型中，**缺参拒调（Abstention）与并行/嵌套调用**是两条极易被忽视的区分度红线：许多经过过度工具微调的小模型在 `Simple` 子集上刷到 92%，一到 `Irrelevance` 子集却依然强行调用最像的接口，把臆造参数写进业务库。评测必须同时报告“应调时召回率”与“不应调时误触发率（False Trigger Rate）”——任何误触发率高于 5% 的底座，都不宜直接授予生产写权限。

::: warning 真实工程事故：嵌套依赖与必填项臆造的双重失灵
某金融投研助手在 BFCL `Simple` 榜单上拿到 91%，上线后却在两条高频指令上频繁翻车：① **并行/嵌套顺序错乱**：用户要求“查出过去 30 天跌幅前三的持仓并分别生成调仓草案”，模型在尚未拿到持仓代码列表前就并发硬猜三个股票代码发出下游调用；② **必填枚举脑补**：用户仅说“帮我查下上月账单”，未说明账户币种，模型没有追问澄清，而是直接把必填字段 `currency` 擅自填成 `"USD"` 并按美元口径出具结论。这两类错误在单轮简单函数测试里几乎完全隐身，只有纳入**嵌套依赖校验**与**缺参拒调专项集**才能提前暴露。
:::

## 9.2 动态 MCP 生态：工具发现、大工具集路由与报错自愈

当企业工具集成统一迁移到<strong><a class="term-ref" href="/books/llm-eval/glossary#mcp" title="MCP（Model Context Protocol）：标准化 Agent 与外部工具服务器、数据源和动态能力发现之间通信的开放协议">模型上下文协议（MCP）</a></strong>后，把 5 个固定函数硬塞进 System Prompt 的评测假设彻底失效。面向真实 MCP 编排的评测必须覆盖三类动态压力场景：

1. <strong>动态工具发现（Tool Discovery）</strong>：评测不再预先暴露全部接口，而是只挂载 MCP Server 目录或元发现工具（如 `list_servers`、`search_tools`、`describe_tool`），考察 Agent 能否在运行时按需拉取目标工具 Schema，并在服务端接口字段微调或新增必填项时自适应完成参数映射。
2. <strong>大工具集检索路由（50–500 Tools 上下文压力）</strong>：中大型企业的 MCP 网关动辄挂载 50 至 500 个工具。如果全量注入上下文，仅 JSON Schema 就会吃掉 20k–60k token，不仅单次 Prefill 账单飙升，还会引发严重的注意力稀释与近似接口混淆（例如把 `refund_order_v2` 误调为 `cancel_order_draft`）。评测必须将检索与决策拆成两段独立指标：
   - <strong>工具检索层（Tool Retriever）</strong>：给定用户请求，Top-$k$ 召回候选工具集合的 $\mathrm{Recall@}k$（是否把正确工具检进了窗口）；
   - <strong>路由与填参层（Selector & Argument Binder）</strong>：在刻意混入 10–30 个高语义相似度干扰工具（Distractor Tools）的上下文里，精准选中唯一目标工具且参数零差错的联合准确率。
3. <strong>工具报错自愈（Error Recovery）</strong>：真实外部微服务必然抖动。评测沙箱应在受控节点主动实施故障注入（Fault Injection），系统覆盖四类高频生产报错——`400 Bad Request`（日期/枚举格式不合规范）、`401 Unauthorized`（需先调用刷新令牌工具）、`429 Too Many Requests`（需退避或切换降级读接口）、`404 / Empty`（需放宽条件二次检索）——并量化两项核心指标：

$$
\mathrm{Recovery\ Rate} = \frac{\text{遭遇受控报错后在 } \le 2 \text{ 轮内修正策略并成功推进的次数}}{\text{触发受控报错的总任务次数}}, \qquad
\mathrm{Graceful\ Abort} = \frac{\text{面对永久性故障能诚实止损转人工的次数}}{\text{注入不可恢复故障的总任务次数}}
$$

| 故障注入类型 | 沙箱模拟响应 | 期望的自愈或止损行为 | 常见失败病理 |
| --- | --- | --- | --- |
| `400 Bad Request` | 返回缺失枚举值或日期格式校验详情 | 解析错误提示，修正参数类型后 1 轮内重试成功 | 原样重发相同错误参数直到步数耗尽 |
| `401 Unauthorized` | 返回会话令牌过期提示 | 主动发现并调用刷新鉴权工具，随后重放原请求 | 直接放弃任务或向用户索要内部系统密钥 |
| `429 / 503 限流超时` | 首次限流、二次恢复或永久宕机 | 瞬态故障切换只读备用接口；永久故障诚实止损转人工 | 假装查询成功并基于参数记忆编造结果 |
| **Schema 字段漂移** | 服务端将 `order_id` 更名为 `order_code` | 重新调用 `describe_tool` 读取新契约并自适应映射 | 死记旧提示词示例持续报字段未定义错 |

工程实践反复证明：能在风平浪静时首调命中的模型比比皆是，但**能在遭遇晦涩报错后读懂堆栈、动态纠偏，并在确实无解时果断止损不胡乱重试**的模型，才是决定生产可用性的真正分水岭。

### 大工具集 MCP 评测的失败拆解公式
面对 200 个动态 MCP 工具，单看端到端成功率完全看不出该优化路由检索还是换模型。建议将单轮工具执行的端到端命中率分解为三段条件概率乘积：

$$
P(\text{Tool Success}) = \underbrace{P(\text{In Top-}k)}_{\text{MCP 检索器召回}} \cdot \underbrace{P(\text{Select Right Tool} \mid \text{In Top-}k)}_{\text{抗近似接口混淆路由}} \cdot \underbrace{P(\text{Valid Args \& Exec} \mid \text{Right Tool})}_{\text{Schema 填参与报错自愈}}
$$

实际企业压测中常见一种极具迷惑性的“Schema 膨胀衰减”：把工具候选数 $k$ 从 10 扩到 80 后，检索器召回率从 86% 涨到 97%，但模型的抗混淆选择准确率却从 93% 暴跌至 68%，导致三者乘积（即便填参执行率维持 100%）仍从 $0.86 \times 0.93 \approx 80.0\%$ 跌至 $0.97 \times 0.68 \approx 66.0\%$，反而净跌 14 个百分点。唯有按三段式解耦画曲线，才能精准定位最优候选窗大小 $k^\star$，避免“工具越塞越多、效果越来越差”。

## 9.3 $\tau$-bench 与 $\tau^2$-bench：政策遵从、终态哈希与 $\mathrm{pass}^k$ 稳定性

要评测“复杂业务政策 + 多轮人机交互 + 状态持久化”的真实综合能力，<strong>τ-bench</strong> 与升级版 <strong>τ²-bench</strong> 确立了行业黄金范式（如图 9-1 所示）：

<figure class="book-figure">
  <img src="/figures/llm-eval/user-simulator-db-eval.svg" alt="多轮工具交互闭环：User Simulator、Agent 与 MCP 及数据库终态哈希校验图" loading="lazy">
  <figcaption><span class="book-figure__label">图 9-1</span>多轮工具交互的闭环测量架构：涵盖用户模拟器、被测 Agent、MCP 与可变数据库，以及 τ²-bench 的双控通道与数据库终态哈希、政策遵从、pass^k 三维判定平面。</figcaption>
</figure>

- <strong>从单控到双控环境（τ-bench → τ²-bench）</strong>：初代 $\tau$-bench（零售退换货、航司改签）中只有 Agent 能调用工具改动数据库，环境是单控的；而 $\tau^2$-bench 引入的电信网络排障等<strong>双控环境（Dual-Control Environment）</strong>中，终端用户同样具备本地工具动作（如重启路由器、切换 SIM 卡、核查手机 APN 设置），环境状态由双方共同驱动。这要求 Agent 不但要准确操作后台 API，还要能拆解清晰步骤指导非专业用户动手操作，并在用户手滑做错时及时通过观测察觉状态分歧——例如用户口头说“我重启好了”，但实则只切了飞行模式而未重启设备，此时 Agent 必须通过状态复核识别口头汇报与真实环境的偏差。
- <strong>数据库终态哈希断言（DB State Hash）</strong>：对话结束后，评测器不锁死中间调用了多少次只读查询，而是直接对任务结束时的可变数据库快照计算规范化哈希 $\mathrm{Hash}(\mathrm{DB}_{\text{final}})$，并与在初始库上回放标准写操作序列得到的 $\mathrm{Hash}(\mathrm{DB}_{\text{gold}})$ 做精确比对。这一设计彻底兼顾了合法路径多样性与结果客观性。
- <strong>业务政策遵从（Policy Compliance）与关键信息断言</strong>：即便最终数据库哈希一致，只要 Agent 触犯了业务政策红线——例如未经用户显式确认就直接执行不可逆取消订单、越权豁免基础经济舱退改手续费、或泄露其他客户隐私——整题立刻判 0 分；同时对纯咨询任务叠加自然语言关键事实断言，核查核心金额、订单号与赔付条款是否准确传达。
- <strong>连续可靠性稳定性剖析（衔接第 2 章）</strong>：多轮随机交互让“偶尔成功一次”彻底失去生产参考价值。沿用 [统计公式速查卡](/books/llm-eval/toolkit/metrics-and-stats) 的无偏组合估计公式，对每道任务独立重复运行 $n$ 次（建议 $n \ge 8$），记通过次数为 $c$，计算连续 $k$ 次全部成功的概率：

$$
\widehat{\mathrm{pass}^k} = \frac{\binom{c}{k}}{\binom{n}{k}} = \prod_{j=0}^{k-1}\frac{c - j}{n - j}
$$

下表用一组典型单次成功率 $p$ 量化 $\mathrm{pass@}k$（探索上限）与 $\mathrm{pass}^k$（生产稳态）之间触目惊心的剪刀差（参见[第 2 章](/books/llm-eval/chapters/chapter-02)交互实验）：

| 单次成功率 $p$ | 探索上限 $\mathrm{pass@}5 = 1-(1-p)^5$ | 连续稳定 $\mathrm{pass}^4 = p^4$ | 连续稳定 $\mathrm{pass}^5 = p^5$ | 连续稳定 $\mathrm{pass}^8 = p^8$ | 生产准入评估 |
| --- | --- | --- | --- | --- | --- |
| $0.50$ | $96.9\%$ | $6.3\%$ | $3.1\%$ | $0.4\%$ | 仅适合录宣传 Demo，上线必遭高频客诉 |
| $0.70$ | $99.8\%$ | $24.0\%$ | $16.8\%$ | $5.8\%$ | 需强人工复核与高风险动作熔断兜底 |
| $0.85$ | $99.99\%$ | $52.2\%$ | $44.4\%$ | $27.2\%$ | 勉强可进入受控低风险业务小流量灰度 |
| $0.95$ | $>99.99\%$ | $81.5\%$ | $77.4\%$ | $66.3\%$ | 达到核心客服/交易流程自动化准入门槛 |

## 9.4 用户模拟器治理：防止“裁判自己放水或坑人”

在全自动多轮评测中，扮演终端客户的<strong><a class="term-ref" href="/books/llm-eval/glossary#user_simulator" title="用户模拟器：在多轮交互评测中扮演真实终端用户的受控语言模型，需严防泄题与过早妥协">用户模拟器（User Simulator）</a></strong>往往是最隐蔽的误差放大器。无数团队在复盘评测分数异常抖动时，最终揪出来的真凶既不是被测模型也不是后端工具，而是“悄悄泄题”或“中途叛变”的模拟器：

| 模拟器典型失真模式 | 真实对话里的具体表现 | 对评测结论的扭曲方向 | 工程治理对策 |
| --- | --- | --- | --- |
| **剧透答案与越权提示** | 直接把内部订单主键、精确工具名甚至退改签政策条款念给 Agent 听 | **假阳性虚高**：评测难度断崖塌陷 | 严格执行信息最小暴露，模拟器提示词彻底隔离后端 Schema 与政策细则 |
| **违背隐性约束** | 人设要求“只接受直飞且预算 $\le 1{,}200$ 元”，聊到第 6 轮却同意了 $1{,}680$ 元中转 | **假阴性错杀**：Agent 照办却通不过终态校验 | 显式注入不可妥协硬约束清单，并做规则前置审查 |
| **过早妥协与早停** | Agent 漏办两项需求中的第二项，礼貌模拟器却提前输出 `###STOP###` 告别 | **漏测追问韧性**：掩盖本应暴露或本可挽救的缺陷 | 引入未完成子目标状态检查，仅全项确认或合规拒办后方允许终止 |
| **同族模型默契偏置** | 用 A 模型扮演模拟器评测 A 模型自己，双方对模糊表达心领神会 | **偏袒同族模型**：扭曲跨厂商横评排名 | 落地<strong>跨模型复核协议（Cross-Model Check）</strong>，至少换用一家异构强模型复跑验证胜负方向 |

::: warning 用户模拟器自身信度审计红线
把用户模拟器本身也当作一把需要校准的“测量仪器”：每次大版本评测必须随机抽取 30–50 条成功与失败轨迹，由人工或独立审计裁判核查<strong>模拟器违规率（Simulator Violation Rate）</strong>。一旦模拟器违规率超过 5%，必须立刻冻结榜单结论、先修复模拟器人设与系统提示；对于已核实的模拟器违规轨迹，严禁直接按 0 分或 1 分混入统计，而应单独分桶剔除或重跑，守住测量信度底线。

同时建议保留一份 20 题<strong>固定脚本金标回放集（Deterministic Golden User Scripts）</strong>，每次升级模拟器提示词或底层模型时先检验模拟器自身在不同 Agent 行为下的顺从度、约束坚守度与终止时机是否发生漂移，确保评测尺子本身跨季度可比。
:::

::: tip 企业自建多轮工单评测集的四步最小闭环
1. 从真实脱敏客服/运维工单中提炼 60–100 组“用户隐性目标卡 + 初始 Mock 数据库快照 + 业务政策文档”；
2. 在隔离 MCP 沙箱里注入 15%–20% 受控接口报错（`400/401/429`）检验自愈与止损能力；
3. 以“数据库终态哈希 ∧ 政策合规检查”为硬判分门禁，每题独立跑 $n=8$ 次报告 $\widehat{\mathrm{pass}^4}$；
4. 用两家异构强模型分别驱动用户模拟器做跨模型复核，确保配对显著性结论稳定不变。
:::

当 Agent 的动作空间从结构化 JSON API 扩展为开放的 Linux Shell 与数十万行真实代码仓库，挑战将瞬间陡增：镜像依赖腐化、Git 历史泄漏与强模型“改测试作弊”成为生死红线。下一章我们深入 Coding / SWE 与终端执行 Agent 评测。
